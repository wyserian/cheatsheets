Linux

Linux is a free and open-source, Unix-like operating system. Strictly speaking, Linux is only the kernel: the core program that manages the hardware. A complete operating system is formed by combining the Linux kernel with GNU tools, system libraries, an init system, and applications, and is shipped as a distribution (distro) such as Ubuntu, Fedora, or Arch.

The kernel was created in 1991 by Linus Torvalds, a student at the University of Helsinki, as a hobby project. It is released under the GNU General Public License v2 (GPLv2) and is developed by thousands of contributors and companies worldwide.

Key Features
  • Open Source : Anyone can read, modify, and redistribute the source code.
  • Multi-User & Multitasking : Many users and processes run at the same time, isolated by permissions.
  • Portable : Runs on almost any hardware: x86, ARM, RISC-V, from tiny embedded boards to supercomputers.
  • Secure & Stable : Strong permission model, fast security updates, and servers that run for years without rebooting.
  • Everything Is a File : Devices, processes, and system settings are exposed as files that can be read and written with normal tools.
  • Shell & Automation : Powerful command-line shells (see the Bash Shell cheatsheet) make every task scriptable.
Where Linux Is Used
  • Servers & Cloud : Runs the majority of web servers and cloud workloads (AWS, Google Cloud, Azure).
  • Mobile : Android is built on the Linux kernel.
  • Supercomputers : All of the world's top 500 supercomputers run Linux.
  • Embedded & IoT : Routers, smart TVs, cars, and Raspberry Pi.
  • Containers : Docker and Kubernetes rely on Linux kernel features (namespaces and cgroups).
  • Desktop : Development and everyday use with distros like Ubuntu, Fedora, and Linux Mint.

UNIX, GNU & Open Source

UNIX

UNIX was created at AT&T Bell Labs in 1969 by Ken Thompson and Dennis Ritchie, and was rewritten in the C language in 1973. Its design ideas, such as small tools that each do one job, pipes, plain-text files, and a hierarchical file system, shaped every modern operating system. Descendants include BSD (FreeBSD, OpenBSD), Solaris, AIX, and macOS. Linux is Unix-like: it follows the same design and standards but contains no original UNIX code.

  • POSIX : An IEEE standard (1988) that defines the common interface of Unix-like systems: system calls, shell, and utilities. Code written for POSIX runs on Linux, macOS, and BSD with little or no change.
  • Unix Philosophy : "Write programs that do one thing and do it well. Write programs to work together."
GNU

The GNU Project ("GNU's Not Unix") was launched in 1983 by Richard Stallman to build a completely free Unix-like operating system. By 1991 GNU had nearly everything (compiler, shell, libraries, utilities) except a working kernel, as its own kernel, GNU Hurd, was unfinished. The Linux kernel filled that gap, and the combination is why some people call the OS GNU/Linux.

Important GNU Components
  • GCC : GNU Compiler Collection, compiles C, C++ and more, including the Linux kernel itself.
  • glibc : GNU C Library, the layer programs use to talk to the kernel.
  • Bash : The default shell on most distributions.
  • Coreutils : Basic commands like ls, cp, mv, cat, chmod.
  • Others : grep, sed, awk (gawk), tar, make, GRUB, Emacs.
Free & Open Source Software
  • Free Software : Defined by the Free Software Foundation (FSF, founded 1985) by four freedoms: to run, study, modify, and share software. "Free" means freedom, not price.
  • Open Source : A similar movement (Open Source Initiative, 1998) that focuses on the practical benefits of open development.
  • GPL (Copyleft) : Anyone who distributes modified GPL software must also release their source code under the GPL. The Linux kernel uses GPLv2.
  • Permissive Licenses : MIT, BSD, and Apache allow use in closed-source products with few conditions.

Linux Kernel

The kernel is the core of the operating system. It is the first program loaded after the bootloader, runs with full control of the hardware, and acts as the bridge between applications and the physical machine. Applications never touch hardware directly; they ask the kernel through system calls.

Responsibilities of the Kernel
  • Process Management : Creates and destroys processes and schedules which one gets the CPU and for how long.
  • Memory Management : Gives each process its own virtual memory, handles paging and swap, and keeps processes from reading each other's memory.
  • Device Drivers : Code that controls hardware such as disks, network cards, GPUs, and USB devices.
  • File Systems : The Virtual File System (VFS) layer provides one interface for many file system types (ext4, XFS, NTFS, network shares).
  • Networking : The full TCP/IP stack, firewall (netfilter), and routing.
  • Security : Users and permissions, plus security modules such as SELinux and AppArmor (see Security & Auditing).
  • System Calls : The interface applications use to request kernel services, e.g. open(), read(), write(), fork(), execve().
Kernel Space vs User Space
  • Kernel Space : Where the kernel runs, with full hardware access (CPU privileged mode, "ring 0"). A bug here can crash the whole system (kernel panic).
  • User Space : Where all applications run, with restricted access ("ring 3"). A crashing program only affects itself.
Application (e.g. cat file.txt)
   -> glibc wrapper function: read()
      -> system call (switch to kernel mode)
         -> VFS -> ext4 driver -> disk driver -> hardware
      <- data returned to user space
Types of Kernels
  • Monolithic Kernel : All core services (drivers, file systems, networking) run together in kernel space. Fast, because components call each other directly. Examples: Linux, traditional UNIX, BSD.
  • Microkernel : Only the bare minimum (scheduling, memory, messaging) runs in kernel space; drivers and file systems run as separate user-space services. More robust but slower due to message passing. Examples: MINIX, QNX, seL4, GNU Hurd.
  • Hybrid Kernel : A mix of both. Examples: Windows NT, macOS (XNU).

Linux is monolithic but modular: drivers can be loaded and unloaded at runtime as kernel modules (.ko files) without rebooting.

uname -r                 # running kernel version, e.g. 6.8.0-45-generic
lsmod                    # list loaded kernel modules
modinfo [module]         # details about a module
sudo modprobe [module]   # load a module (with its dependencies)
sudo modprobe -r [module] # unload a module
dmesg                    # kernel messages (ring buffer)
cat /proc/version        # kernel build information
Kernel Versions
  • Mainline : The newest development version, maintained by Linus Torvalds; a new release about every 9-10 weeks.
  • Stable : Bug-fix updates to recent releases.
  • Longterm (LTS) : Selected versions maintained for several years; used by most distributions and Android.

All versions are published at kernel.org. The kernel is written mostly in C, with Rust supported for new drivers since version 6.1.

Linux Architecture

A Linux system is built in layers. Each layer only talks to the layer directly below it.

+--------------------------------------------------------+
|  Applications     browsers, editors, servers, games    |
+--------------------------------------------------------+
|  Shell & Utilities   bash, ls, grep, GUI desktop       |
+--------------------------------------------------------+
|  System Libraries  glibc  (system call wrappers)        |
+========================================================+  user space
|  Kernel   process | memory | drivers | VFS | network    |  kernel space
+--------------------------------------------------------+
|  Hardware   CPU, RAM, disk, network card, devices       |
+--------------------------------------------------------+
Components of a Linux System
  • Hardware : The physical machine: CPU, memory, storage, and peripherals.
  • Kernel : Manages all hardware and resources (see Linux Kernel).
  • Bootloader : Loads the kernel into memory at startup, e.g. GRUB.
  • Init System : The first user-space process (PID 1), which starts and supervises all other services. Most distros use systemd.
  • Daemons : Background services such as sshd (remote login), cron (scheduler), and web servers. Names often end in "d".
  • System Libraries : Shared code that programs use, mainly glibc.
  • Shell : Command-line interface to the system, e.g. Bash, Zsh.
  • Display Server : Draws graphics on screen: X11 (Xorg) or the newer Wayland.
  • Desktop Environment : The graphical interface: GNOME, KDE Plasma, XFCE, Cinnamon. Servers usually have none.
  • Applications : Everything the user runs on top.

Boot Process

Power On -> BIOS/UEFI -> Bootloader (GRUB) -> Kernel + initramfs -> init (systemd) -> Target -> Login
  1. BIOS / UEFI : Firmware runs the Power-On Self-Test (POST), finds a bootable disk, and starts the bootloader. UEFI is the modern replacement for BIOS and supports Secure Boot.
  2. Bootloader (GRUB 2) : Shows the boot menu, then loads the kernel image (/boot/vmlinuz-*) and the initial RAM disk (initramfs) into memory.
  3. Kernel : Decompresses itself, detects hardware, loads drivers, and uses the initramfs to mount the real root file system.
  4. Init (systemd, PID 1) : Starts all services in parallel according to their dependencies.
  5. Target : systemd reaches the default target: multi-user.target (text mode, servers) or graphical.target (desktop).
  6. Login : A text login prompt (getty) or a graphical display manager (GDM, SDDM) appears.
Runlevels vs systemd Targets
Runlevel (SysV init) systemd Target Description
0 poweroff.target shut down
1 rescue.target single-user rescue mode
3 multi-user.target multi-user, text mode with networking
5 graphical.target multi-user with graphical desktop
6 reboot.target reboot 
systemctl get-default                        # current default target
sudo systemctl set-default multi-user.target # boot to text mode
systemd-analyze blame                        # which services slowed down boot

Distributions

A distribution (distro) packages the Linux kernel with GNU tools, a package manager, an installer, default software, and usually a desktop. Distros differ mainly in package format, release model, and target audience.

Types of Release Models
  • Fixed / Point Release : Major versions released on a schedule, then only security and bug fixes. Stable and predictable. Examples: Debian, Ubuntu, RHEL.
  • LTS (Long Term Support) : Fixed releases supported for many years, e.g. Ubuntu LTS (5 years of standard support, released every 2 years in April).
  • Rolling Release : Continuous updates with no major versions; always the latest software. Examples: Arch, openSUSE Tumbleweed.
Choosing a Distro
  • Beginners / Desktop : Ubuntu, Linux Mint, Fedora Workstation.
  • Servers : Ubuntu Server, Debian, RHEL, Rocky Linux, AlmaLinux.
  • Security & Pentesting : Kali Linux, Parrot OS.
  • Containers : Alpine (very small image), Debian slim, Ubuntu.
  • Learning Internals : Arch Linux, Gentoo.

Linux File System

Linux uses a single directory tree starting at the root /. There are no drive letters: extra disks and USB drives are mounted into a folder of this tree. File names are case-sensitive (File.txt and file.txt are different), and names starting with a dot (.bashrc) are hidden.

Filesystem Hierarchy Standard (FHS)
Directory Contents
/ root of the entire file system
/bin essential command binaries for all users (ls, cp, bash); a link to /usr/bin on modern distros
/boot bootloader files: kernel image (vmlinuz), initramfs / initrd, GRUB configuration
/dev device files for hardware and partitions, e.g. /dev/sda (disk), /dev/null
/etc system-wide configuration files and scripts
/home home directories of regular users (/home/username)
/lib, /lib64 shared libraries for the binaries in /bin and /sbin, and kernel modules
/lost+found files recovered by fsck after a crash; one per partition (ext file systems)
/media mount points for removable media (USB, CD), mounted automatically
/mnt mount point for temporarily mounted file systems (manual mounts)
/net access to directory trees on remote NFS servers (automounter); found on some systems, not part of the FHS
/opt optional, large add-on application software packages
/proc virtual file system with kernel and process information (e.g. /proc/cpuinfo)
/root home directory of the root user
/run runtime data since the last boot (PID files, sockets)
/sbin essential system binaries and administration commands (fdisk, reboot); a link to /usr/sbin on modern distros
/srv data for services provided by the system (web, FTP)
/sys virtual file system exposing devices and kernel settings
/tmp temporary files, often cleared on reboot
/usr user utilities and applications (read-only, shareable)
/usr/bin non-essential command binaries for all users
/usr/lib libraries for the binaries in /usr/bin and /usr/sbin
/usr/sbin non-essential system binaries (daemons and services)
/usr/share architecture-independent data (documentation, man pages, icons)
/usr/src source code (e.g. kernel sources)
/usr/local software installed locally by the administrator, outside the package manager
/usr/local/bin local software binaries
/usr/local/games local game binaries
/usr/local/include local C header files
/usr/local/lib local libraries for the binaries in /usr/local/bin and /usr/local/sbin
/usr/local/man local manual pages
/usr/local/sbin local system binaries
/usr/local/share local architecture-independent data
/usr/local/src local source code
/var variable files that change while running: logs (/var/log), caches, mail spools, databases, websites (/var/www)
Paths
  • Absolute Path : Starts from root: /home/rahul/docs/notes.txt.
  • Relative Path : Starts from the current directory: docs/notes.txt, ../backup.
  • Special Names : . current directory, .. parent directory, ~ home directory, - previous directory (with cd).
Types of Files

The first character of ls -l output shows the file type.

Symbol File Type Example
- regular file text, images, binaries
d directory /home
l symbolic link /bin -> usr/bin
c character device (data one character at a time) /dev/tty, /dev/null
b block device (data in blocks) /dev/sda, /dev/nvme0n1
s socket (process communication) /run/docker.sock
p named pipe (FIFO) created with mkfifo
Types of File Systems
  • ext4 : The default on Debian and Ubuntu. Mature, reliable, journaling file system.
  • XFS : High-performance journaling file system for large files; default on RHEL.
  • Btrfs : Copy-on-write file system with snapshots, compression, and checksums; default on Fedora and openSUSE.
  • ZFS : Advanced file system and volume manager with strong data integrity; available as a separate module due to licensing.
  • FAT32 / exFAT : For USB drives and SD cards shared with Windows and macOS.
  • NTFS : Windows file system; supported through the in-kernel ntfs3 driver.
  • tmpfs : File system stored in RAM, used for /tmp and /run.
  • swap : Disk space used as overflow memory when RAM is full.
  • NFS / SMB : Network file systems for sharing folders across machines.
Inodes & Links

An inode stores a file's metadata (permissions, owner, size, timestamps, location of data blocks) but not its name. A directory is a list that maps names to inode numbers.

  • Hard Link : Another name pointing to the same inode. The data remains until every hard link is deleted. Cannot cross file systems or link to directories. ln file.txt hard.txt
  • Soft (Symbolic) Link : A small file that stores a path to another file, like a shortcut. Can cross file systems and point to directories, but breaks if the target is moved or deleted. ln -s /var/log logs
ls -i file.txt           # show inode number
stat file.txt            # full inode details
df -i                    # inode usage per file system
Disks & Mounting
lsblk                          # list disks and partitions
df -h                          # free space per mounted file system
du -sh [dir]                   # total size of a directory
sudo fdisk -l                  # partition tables
sudo mount /dev/sdb1 /mnt/usb  # mount a partition
sudo umount /mnt/usb           # unmount it
findmnt                        # tree of all mounts
cat /etc/fstab                 # file systems mounted automatically at boot
sudo mkfs.ext4 /dev/sdb1       # format a partition as ext4 (erases data)

Users & Groups

Linux is multi-user: every file and process belongs to a user and a group. Each user has a numeric UID, and each group a GID.

  • root (UID 0) : The superuser, with unrestricted access to the whole system.
  • System Users : Accounts for services such as www-data or mysql (UID usually below 1000), with no login shell.
  • Regular Users : Human users (UID 1000 and above on most distros).
  • sudo : Lets permitted users run a single command as root, logging what they do. Users in the sudo group (Debian/Ubuntu) or wheel group (Fedora/RHEL/Arch) can use it.
Account Files
  • /etc/passwd : user list, format name:x:UID:GID:comment:home:shell.
  • /etc/shadow : hashed passwords and password expiry (readable by root only; format in Authentication & PAM).
  • /etc/group : groups and their members.
  • /etc/sudoers : sudo rules; always edit it with sudo visudo.
Commands Description
whoami print current user
id [user] print user ID, group ID and groups
groups [user] print groups a user belongs to
who / users print logged in users
w print who is logged in and what they are running
last history of logins
sudo [command] superuser do - run a command with root privileges
sudo -i open a root shell
su - [user] switch user - log in as another user (root if omitted)
passwd [user] change password
sudo useradd -m -s /bin/bash [user] create user with a home directory and Bash shell
sudo usermod -aG [group] [user] add user to a group (-a keeps existing groups)
sudo userdel -r [user] delete user and their home directory
sudo groupadd [group] create a group

File Permissions

Every file has an owner (user), a group, and three sets of permissions: for the owner, for the group, and for everyone else (others).

Format of Permission
-rwxr-xr--  1  rahul  dev  4096  Oct 19 10:00  script.sh
|\_/\_/\_/      owner  group
| |  |  |
| |  |  +-- others permission
| |  +----- group permission
| +-------- user (owner) permission
+---------- file type
Options Description
File Type - (regular file), d (directory), l (symbolic link), c (character device), b (block device)
Setting Permission + (add), - (remove), = (assign exactly)
Permission r (read), w (write), x (execute), - (no permission)
Who u (user/owner), g (group), o (others), a (all three)
Meaning for Files vs Directories
  • r : read the file's contents / list the directory's entries.
  • w : modify the file / create, delete or rename files inside the directory.
  • x : run the file as a program / enter the directory with cd.
chmod (Symbolic)
Syntax
chmod [who][+-=][permission] [file]
chmod -R [who][+-=][permission] [dir]     # change recursively
Example
chmod u+x script.sh          # owner can execute
chmod go-w notes.txt         # remove write for group and others
chmod a=r report.pdf         # everyone read-only
chmod u=rwx,g=rx,o= app      # set all three at once
chmod (Numeric / Octal)
Permission Value
r 4
w 2
x 1
- 0
Permission Value Permission Description
7 rwx read, write & execute
6 rw- read & write
5 r-x read & execute
4 r-- read-only
3 -wx write & execute
2 -w- write only
1 --x execute only
0 --- none

Note : max value is r+w+x = 4+2+1 = 7. One digit each for user, group and others.

  • rwx rwx --- = 4+2+1 4+2+1 0+0+0 = 770
  • r-x r-- r-- = 4+0+1 4+0+0 4+0+0 = 544
Example
chmod 755 script.sh     # rwxr-xr-x : owner full, others read & run (scripts, folders)
chmod 644 notes.txt     # rw-r--r-- : owner edits, others read (normal files)
chmod 600 ~/.ssh/id_rsa # rw------- : private to owner (SSH keys)
Avoid chmod 777: it lets every user on the system modify or replace the file.
Ownership
sudo chown rahul file.txt          # change owner
sudo chown rahul:dev file.txt      # change owner and group
sudo chown -R www-data /var/www    # recursively
sudo chgrp dev file.txt            # change group only
Special Permissions
Permission Value Effect
SUID (s in user x) 4000 program runs with the file owner's privileges, e.g. /usr/bin/passwd runs as root
SGID (s in group x) 2000 on a directory, new files inherit the directory's group (shared team folders)
Sticky Bit (t in others x) 1000 on a directory, users can only delete their own files, e.g. /tmp 
chmod u+s [file]     # or chmod 4755 [file]
chmod g+s [dir]      # or chmod 2775 [dir]
chmod +t [dir]       # or chmod 1777 [dir]
umask

The umask removes permissions from newly created files. With the common default 022, new files get 644 and new directories get 755.

umask          # show current mask
umask 027      # new files 640, new directories 750

Authentication & PAM

Linux does not have one central authentication service like Windows' LSASS. Instead, every program that logs users in (login, sshd, sudo, the graphical login screen) hands authentication to PAM, a shared library, so the rules are configured once and reused everywhere.

Login Flow
getty / display manager (GDM, SDDM) / sshd
   -> PAM  auth      : verify the user (password, key, MFA)
   -> PAM  account   : is the account allowed now? (expired, locked, time limits)
   -> PAM  session   : set up the session (limits, mount home, start keyring)
   -> user's shell starts with their UID, GID and groups
PAM (Pluggable Authentication Modules)

Each service has a config file in /etc/pam.d/ (e.g. sshd, sudo, login). Shared rules live in common-auth etc. on Debian/Ubuntu and in system-auth on Fedora/RHEL. Each line is a type, a control flag, and a module.

Module Types
  • auth : proves identity (password, OTP, hardware key).
  • account : checks whether the account may log in (expiry, lockout, access rules).
  • password : rules for changing passwords (strength, hashing).
  • session : runs actions at login and logout (resource limits, logging, keyring unlock).
Control Flags
  • required : must succeed; on failure the rest still runs, then the whole stack fails.
  • requisite : must succeed; on failure stop immediately.
  • sufficient : success is enough by itself (if nothing required failed before it).
  • optional : result only matters if it is the only module.
  • include : pull in rules from another file.
Example
#type     control     module              arguments
auth      required    pam_faillock.so     preauth            # lock after repeated failures
auth      required    pam_unix.so                            # check /etc/shadow
auth      required    pam_u2f.so                             # plus a hardware security key (MFA)
account   required    pam_unix.so
password  requisite   pam_pwquality.so    retry=3 minlen=12  # password strength
password  required    pam_unix.so         use_authtok sha512 shadow
session   required    pam_limits.so                          # apply /etc/security/limits.conf
Common Modules
  • pam_unix.so : classic passwords from /etc/passwd and /etc/shadow.
  • pam_faillock.so : account lockout after failed attempts (faillock --user [name] to view, --reset to unlock).
  • pam_pwquality.so : password strength rules.
  • pam_google_authenticator.so / pam_u2f.so : one-time codes / FIDO2 security keys for MFA.
  • pam_sss.so : central accounts through SSSD (LDAP, Kerberos, Active Directory).
  • pam_limits.so : per-user resource limits.
A mistake in /etc/pam.d/ can lock everyone out, including root. Keep a root shell open while editing and test the login in a second session before closing it.
Password Hashes (/etc/shadow)
rahul:$y$j9T$Fq3...salt...$Wd8...hash...:20015:0:99999:7:::
 |     |   |       |           |           |   | |     |
 |     |   |       |           |           |   | |     +-- warn days before expiry
 |     |   |       |           |           |   | +-------- max days between changes
 |     |   |       |           |           |   +---------- min days between changes
 |     |   |       |           |           +-------------- last change (days since 1970-01-01)
 |     |   |       |           +-------------------------- hash
 |     |   |       +-------------------------------------- salt
 |     |   +---------------------------------------------- params
 |     +-------------------------------------------------- algorithm ID
 +-------------------------------------------------------- username
ID Algorithm Notes
$y$ yescrypt current default on Debian 11+, Ubuntu 22.04+, Fedora 35+; memory-hard
$6$ SHA-512 crypt long-time default, still common (e.g. RHEL)
$5$ SHA-256 crypt less common
$2b$ bcrypt used by some distros and BSDs
$1$ MD5 crypt obsolete and weak; flag in audits
! or * none account locked, or password login disabled

Unlike the Windows NT hash, every Linux hash includes a random salt, so two users with the same password get different hashes, and precomputed (rainbow table) attacks do not work.

Password Ageing & Locking
sudo chage -l rahul         # show password ageing info
sudo chage -M 90 rahul      # password must change every 90 days
sudo chage -d 0 rahul       # force a password change at next login
sudo passwd -l rahul        # lock the password (adds ! to the hash)
sudo passwd -u rahul        # unlock
sudo passwd -S rahul        # password status
NSS & Central Accounts

PAM decides how a user proves who they are; NSS (Name Service Switch) decides where user and group information is looked up. /etc/nsswitch.conf lists the sources in order, e.g. passwd: files sss (local files first, then SSSD).

  • SSSD : System Security Services Daemon. Connects Linux to LDAP, FreeIPA, or Active Directory, and caches credentials so users can log in while offline.
  • Kerberos : the same ticket protocol Windows domains use; config in /etc/krb5.conf.
  • realmd : joins a machine to an AD or FreeIPA domain in one command.
getent passwd rahul                      # look up a user through NSS (local or domain)
sudo realm discover corp.example.com     # find the domain
sudo realm join corp.example.com -U admin  # join Active Directory
id rahul@corp.example.com                # domain user's UID and groups
kinit rahul@CORP.EXAMPLE.COM             # get a Kerberos ticket
klist                                    # list Kerberos tickets

SSH & Key-Based Auth

SSH (Secure Shell) is the standard way to log in to and manage Linux machines remotely. It encrypts the whole session and supports password, public-key, and certificate authentication. Key-based authentication is the recommended method: it is stronger than passwords and cannot be brute-forced.

How Key Authentication Works
1. Client connects; server proves its identity with its host key
   (client checks ~/.ssh/known_hosts, asks "trust this host?" the first time)
2. Client offers a public key; server looks for it in ~/.ssh/authorized_keys
3. Client signs data with its PRIVATE key (which never leaves the client)
4. Server verifies the signature with the stored PUBLIC key -> logged in
Key Types
  • Ed25519 : modern, fast, short keys. Recommended default.
  • RSA : widely compatible; use 3072 or 4096 bits.
  • ECDSA : elliptic curve; fine, but Ed25519 is preferred.
  • Ed25519-SK / ECDSA-SK : keys stored on a FIDO2 hardware key (YubiKey); require a physical touch to use.
ssh-keygen -t ed25519 -C "rahul@laptop"   # create a key pair (set a passphrase)
ssh-keygen -t ed25519-sk                  # key on a hardware security key
ssh-copy-id rahul@server                  # install your public key on a server
ssh -i ~/.ssh/id_ed25519 rahul@server     # log in with a specific key
ssh-keygen -lf ~/.ssh/id_ed25519.pub      # show key fingerprint
ssh-keygen -R server                      # remove an old host key from known_hosts
Files & Required Permissions
File Purpose Permission
~/.ssh/ SSH folder 700
~/.ssh/id_ed25519 private key (never share) 600
~/.ssh/id_ed25519.pub public key (safe to share) 644
~/.ssh/authorized_keys public keys allowed to log in as this user 600
~/.ssh/known_hosts fingerprints of servers you trust 644
/etc/ssh/sshd_config SSH server configuration 644 (root-owned)

sshd refuses keys if these files are writable by other users. A line in authorized_keys can be restricted with options, e.g. from="10.0.0.0/8",command="/usr/local/bin/backup" ssh-ed25519 AAAA....

ssh-agent

The agent keeps decrypted private keys in memory, so you type the passphrase once per session.

eval "$(ssh-agent -s)"           # start the agent
ssh-add ~/.ssh/id_ed25519        # add a key (asks for the passphrase)
ssh-add -l                       # list loaded keys
ssh-add -D                       # remove all keys

Agent forwarding (ssh -A) lets a remote server use your agent. Root on that server can then use your keys while you are connected, so prefer ssh -J jumphost target (ProxyJump) instead.

Server Hardening (sshd_config)
PermitRootLogin no               # log in as a user, then use sudo
PasswordAuthentication no        # keys only (set up keys first!)
PubkeyAuthentication yes
KbdInteractiveAuthentication no
MaxAuthTries 3
AllowUsers rahul deploy          # only these users may log in
X11Forwarding no
sudo sshd -t                     # test the config for errors before reloading
sudo systemctl reload ssh        # Debian/Ubuntu ("sshd" on Fedora/RHEL/Arch)

Tools like fail2ban block IPs after repeated failed logins.

Credential Storage

Linux has no single built-in vault like Windows Credential Manager. Desktops use the Secret Service standard, and command-line tools use agents and encrypted stores.

Secret Service (Keyrings)

The Secret Service API (freedesktop.org standard, accessed through libsecret) is the desktop credential store. Browsers, Git, email clients, and Wi-Fi settings save passwords there. It is implemented by:

  • GNOME Keyring : default on GNOME; manage it with the Seahorse app ("Passwords and Keys").
  • KWallet : default on KDE Plasma.
  • KeePassXC : can also act as a Secret Service provider.

The default "login" keyring is encrypted with the user's login password and unlocked automatically at login by a PAM module (pam_gnome_keyring.so or pam_kwallet5.so). This plays the role DPAPI plays on Windows.

secret-tool store --label="My API" service myapp user rahul   # save (prompts for secret)
secret-tool lookup service myapp user rahul                   # read it back
secret-tool clear service myapp user rahul                    # delete it
pass (Password Store)

The standard Unix password manager: each secret is a GPG-encrypted file in ~/.password-store, which can be synced with Git.

pass init [gpg-key-id]           # create the store
pass insert email/gmail          # add a password
pass show email/gmail            # decrypt and show
pass -c email/gmail              # copy to clipboard (cleared after 45 s)
pass generate web/github 20      # generate a 20-character password
Agents
  • ssh-agent : holds decrypted SSH keys in memory (see SSH).
  • gpg-agent : caches GPG passphrases; can also serve as the SSH agent.
  • SSSD cache : stores hashed domain credentials so domain users can log in offline.
Git Credentials
git config --global credential.helper libsecret          # store in the desktop keyring (if installed)
git config --global credential.helper 'cache --timeout=3600'  # in memory for 1 hour
git config --global credential.helper store              # PLAINTEXT in ~/.git-credentials (avoid)

Git Credential Manager (GCM) is a cross-platform alternative that uses the keyring and supports browser sign-in.

Service Credentials

systemd-creds encrypts secrets for services (optionally bound to the TPM), so they are not stored as plain files.

echo -n "s3cret" | sudo systemd-creds encrypt --name=dbpass - dbpass.cred
# in the unit file:  LoadCredentialEncrypted=dbpass:/etc/myapp/dbpass.cred
# the service reads it from $CREDENTIALS_DIRECTORY/dbpass
Plaintext Credentials to Audit

Secrets often end up in plain files. Auditors check:

  • ~/.bash_history : passwords typed on the command line (e.g. mysql -p[password]).
  • ~/.git-credentials, ~/.netrc, ~/.pgpass : saved logins.
  • ~/.aws/credentials, ~/.kube/config, ~/.docker/config.json : cloud and container tokens.
  • .env files and app config in /var/www, /opt : database passwords and API keys.
  • /proc/[PID]/environ : environment variables of running processes (readable by the owner and root).

Security & Auditing

Mandatory Access Control (SELinux & AppArmor)

Normal file permissions are Discretionary Access Control (DAC): the file owner decides who has access. Mandatory Access Control (MAC) adds system-wide rules that even root processes must follow, so a compromised web server can only touch the files its policy allows.

  • SELinux : used by Fedora, RHEL, and Android. Every file and process has a security label (context), and policy rules decide which labels may interact. Modes: enforcing, permissive (log only), disabled.
  • AppArmor : used by Ubuntu, Debian, and SUSE. Simpler path-based profiles per program, stored in /etc/apparmor.d/. Modes: enforce, complain (log only).
# SELinux
getenforce                       # Enforcing / Permissive / Disabled
sestatus                         # full status
ls -Z /var/www                   # file labels
ps -eZ | grep httpd              # process labels
sudo restorecon -Rv /var/www     # reset labels to policy defaults (fixes most errors)
sudo ausearch -m avc -ts recent  # recent denials
sudo setenforce 0                # permissive until reboot (for troubleshooting only)

# AppArmor
sudo aa-status                   # loaded profiles and their mode
sudo aa-complain /usr/sbin/nginx # log only for one program
sudo aa-enforce /usr/sbin/nginx  # enforce again
Disabling SELinux or AppArmor to "fix" an error is a common audit finding. Fix the label or the profile instead.
Linux Capabilities

Capabilities split root's power into separate privileges that can be given to a single program, similar to Windows privileges. A web server can bind port 80 without running as root.

Capability Allows
CAP_NET_BIND_SERVICE bind to ports below 1024
CAP_NET_RAW raw sockets (used by ping)
CAP_DAC_OVERRIDE bypass file read/write/execute permission checks
CAP_SETUID change user ID, effectively becoming root
CAP_SYS_ADMIN a huge set of admin operations (nearly root) 
getcap -r / 2>/dev/null                            # find all files with capabilities
sudo setcap cap_net_bind_service=+ep /usr/bin/myapp # grant one capability
sudo setcap -r /usr/bin/myapp                       # remove capabilities
grep Cap /proc/self/status                          # capabilities of the current process

An interpreter (python, perl, node) with cap_setuid or cap_dac_override is a privilege-escalation risk and should be flagged.

sudo Rules

Rules in /etc/sudoers and /etc/sudoers.d/ follow the format who where=(as_whom) what. Always edit with sudo visudo, which checks syntax before saving.

rahul   ALL=(ALL:ALL) ALL                                  # full sudo, password required
%admins ALL=(ALL) ALL                                      # everyone in group "admins"
deploy  ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp  # one command, no password
sudo -l                    # what am I allowed to run?
sudo -l -U deploy          # rules for another user (as root)

Audit risks : NOPASSWD: ALL, wildcards in commands, and sudo access to editors, pagers, or interpreters (vim, less, find, python), which can open a root shell.

Boot & Disk Security
  • Secure Boot : UEFI firmware loads shim (signed by Microsoft), which verifies the distro-signed GRUB and kernel. Custom kernel modules must be signed with a MOK (Machine Owner Key) enrolled with mokutil.
  • Kernel Lockdown : with Secure Boot on, the kernel blocks actions that could modify it at runtime, such as loading unsigned modules or writing to /dev/mem.
  • LUKS : standard full-disk encryption (the Linux counterpart of BitLocker), managed with cryptsetup.
  • TPM : can unlock LUKS automatically only if the boot chain is unchanged (sealed to PCR values), like BitLocker with TPM.
mokutil --sb-state                         # is Secure Boot enabled?
cat /sys/kernel/security/lockdown          # kernel lockdown mode
sudo cryptsetup luksDump /dev/nvme0n1p3    # LUKS header and key slots
sudo cryptsetup luksFormat /dev/sdb1       # encrypt a partition (erases data)
sudo cryptsetup open /dev/sdb1 secure      # unlock as /dev/mapper/secure
sudo systemd-cryptenroll --tpm2-device=auto /dev/nvme0n1p3   # unlock with the TPM

For the host firewall (ufw, firewalld), see Networking.

Authentication Logs
sudo tail -f /var/log/auth.log           # Debian/Ubuntu: logins, sudo, SSH
sudo tail -f /var/log/secure             # Fedora/RHEL equivalent
journalctl -u ssh --since today          # SSH logs via systemd ("sshd" on RHEL)
journalctl _COMM=sudo                    # every sudo command
last                                     # successful login history (/var/log/wtmp)
sudo lastb                               # failed login attempts (/var/log/btmp)

Log Message Meaning

Invalid user [name] from [IP] login attempt for a user that does not exist

session opened for user root a root session started (via su, sudo, or login)
auditd (Linux Audit Framework)

The kernel audit system records security-relevant events (file access, system calls, logins) according to rules, the Linux counterpart of Windows audit policy. Events are written to /var/log/audit/audit.log.

sudo auditctl -w /etc/shadow -p wa -k shadow-change    # watch writes/attribute changes
sudo auditctl -w /etc/sudoers -p wa -k sudoers-change
sudo auditctl -l                                       # list active rules
sudo ausearch -k shadow-change                         # find events by key
sudo aureport --auth                                   # authentication report
sudo aureport --failed                                 # failed events summary
# make rules permanent in /etc/audit/rules.d/*.rules
Where Persistence Hides (Audit Checklist)
  • Accounts : extra UID 0 users (awk -F: '$3 == 0' /etc/passwd), accounts with empty passwords, unexpected sudoers entries.
  • SSH Keys : unknown entries in ~/.ssh/authorized_keys and /root/.ssh/authorized_keys.
  • Scheduled Jobs : /etc/crontab, /etc/cron.*/, /var/spool/cron/, and systemd timers (systemctl list-timers).
  • Services : new units in /etc/systemd/system/ and ~/.config/systemd/user/.
  • Shell Startup Files : ~/.bashrc, ~/.profile, /etc/profile.d/.
  • SUID/SGID & Capabilities : find / -perm -4000 -type f 2>/dev/null and getcap -r /; compare with a known-good list.
  • Library Preloading : /etc/ld.so.preload or an LD_PRELOAD variable injects a library into every program.
  • Kernel Modules : unexpected entries in lsmod.
  • Writable PATH : directories in $PATH writable by normal users.
Audit & Hardening Tools
  • Lynis : security audit and hardening suggestions (sudo lynis audit system).
  • AIDE : file integrity monitoring; alerts when system files change.
  • rkhunter / chkrootkit : scan for known rootkits.
  • fail2ban : bans IPs with repeated failed logins.
  • CIS Benchmarks : industry-standard hardening checklists per distribution.

Run audit and offensive-style checks only on systems you own or are authorized to assess.

Processes & Signals

A process is a running instance of a program. Each has a unique Process ID (PID) and a parent (PPID). The first process, systemd (PID 1), is the ancestor of all others. A daemon is a process that runs in the background without a terminal.

Process States
  • R (Running) : Running or ready to run.
  • S (Sleeping) : Waiting for an event, such as user input.
  • D (Uninterruptible Sleep) : Waiting for I/O, usually disk; cannot be killed until it finishes.
  • T (Stopped) : Paused, e.g. with Ctrl + Z.
  • Z (Zombie) : Finished, but its parent has not yet collected its exit status.
Commands Description
ps snapshot of processes in current terminal
ps aux all processes with user, CPU and memory usage
ps -ef all processes with PID and PPID
pstree processes as a parent-child tree
top view running processes in real time interactively
htop friendlier interactive process viewer (may need installing)
pgrep [name] find PIDs by process name
kill [PID] send SIGTERM (polite stop request) to a process
kill -9 [PID] send SIGKILL (force kill, last resort)
pkill [name] / killall [name] kill processes by name
nice -n 10 [command] start with lower priority (-20 highest to 19 lowest)
renice 5 -p [PID] change priority of a running process
Signals

Signals are messages the kernel or another process sends to a process. List them all with kill -l.

Signal Number Meaning
SIGHUP 1 terminal closed; many daemons reload their config on it
SIGINT 2 interrupt from keyboard (Ctrl + C)
SIGKILL 9 kill immediately; cannot be caught or ignored
SIGTERM 15 request to terminate gracefully (default for kill)
SIGCONT 18 continue a stopped process
SIGSTOP 19 pause a process; cannot be caught or ignored
SIGTSTP 20 pause from keyboard (Ctrl + Z)

Always try kill (SIGTERM) first so the program can save data and clean up; use kill -9 only if it does not respond. Process details live in /proc/[PID]/.

Text Processing

Linux tools are built to be chained with pipes: each reads text, transforms it, and passes it on.

Grep

Global regular expression print (grep) prints lines that match a pattern in text or files.

Syntax
grep [options] [pattern] [file]
  • grep hello file.txt : print lines containing "hello" in file.txt
  • grep -i hello file.txt : case insensitive match
  • grep -r hello ./src : search recursively in all files under ./src
  • grep -v hello file.txt : print lines that do not contain "hello"
  • grep -c hello file.txt : count matching lines
  • grep -w hello file.txt : match whole word "hello" only (not "helloworld")
  • grep -n hello file.txt : print line numbers with matched lines
  • grep -l hello * : print only the names of files that contain a match
  • grep -o "[0-9]\+" file.txt : print only the matched part, not the whole line
  • grep -B 2 -A 3 hello file.txt : print 2 lines before and 3 lines after each match
  • grep -E "error|warn" app.log : extended regex, match either word
Regular Expressions

A regular expression (regex) is a pattern for matching text. Use grep -E for extended regex, where + ? | ( ) { } work without backslashes.

Pattern Matches
^ / $ start / end of line
. any single character
* zero or more of the previous item
+ / ? one or more / zero or one (extended regex)
[abc] / [^abc] one character in / not in the set
[0-9], [a-z] one character in the range
{n} / {n,m} exactly n / between n and m repetitions (extended regex)
a|b a or b (extended regex)
\b word boundary
Example
  • grep '^The' file.txt : lines starting with "The"
  • grep 'end$' file.txt : lines ending with "end"
  • grep '[Hh]ello' file.txt : "Hello" or "hello"
  • grep -E 'hello|HELLO' file.txt : "hello" or "HELLO"
  • grep -E '[0-9]{4}' file.txt : a 4 digit number
  • grep -E '^[a-z0-9._]+@[a-z]+\.[a-z]{2,}$' emails.txt : simple email format
  • grep -v '^#' config.conf | grep -v '^$' : drop comment and empty lines
Tr

Translate, squeeze, and/or delete characters from standard input and write them to standard output.

Syntax
tr [options] [set1] [set2]
  • tr "ab" "xy" <<< "abcd" : replace "a" with "x" and "b" with "y" (xycd)
  • tr 'a-z' 'A-Z' <<< "abcd" : convert lower case characters to upper case
  • tr '[:lower:]' '[:upper:]' <<< "abcd" : convert lower case characters to upper case
  • tr '[:space:]' '\t' <<< "Hello World" : translate white-space characters to tabs
  • tr -s 'a-z' <<< "Hellooo Worrld" : squeeze repeated characters into one (Helo World)
  • tr -d "l" <<< "Hello World" : delete specified characters (Heo Word)
  • tr -d '[:digit:]' <<< "Hello 123 World6789" : remove all the digits from the string
  • tr -c "a" "x" <<< "ababc" : replace every character except "a" (complement with -c)
  • tr -cd '[:digit:]' <<< "abc123def456" : delete everything except digits (123456)

Find & Search

Find

Searches for files and directories in a directory tree, by name, type, size, time, owner, or permissions, and can run commands on the results.

Syntax
find [path] [conditions] [action]
  • find . -name file.txt : find "file.txt" (case sensitive)
  • find . -iname file.txt : find "file.txt" (case insensitive)
  • find . -name "*.html" : find files ending with ".html" (quote the pattern)
  • find . -maxdepth 2 -name "*.cpp" : search only 2 directory levels deep
  • find . -not -name "*.cpp" : find everything except ".cpp" files
  • find . -type f / -type d : only files / only directories
  • find / -size +100M : files larger than 100 MB
  • find . -empty : empty files and directories
  • find / -mtime -10 : modified within the last 10 days (+10 = more than 10 days ago)
  • find / -atime -10 : accessed within the last 10 days
  • find / -mmin -30 : modified within the last 30 minutes
  • find / -cmin -10 : status (permissions, owner) changed within the last 10 minutes
  • find /home -user rahul : files owned by a user
  • find / -perm -4000 : files with the SUID bit set
  • find . -name "*.log" -exec rm {} \; : run a command on each result
  • find . -name "*.tmp" -delete : delete matching files

Add 2>/dev/null to hide "Permission denied" errors when searching from /.

Other Search Tools
  • locate [file] : very fast name search using a database (refresh it with sudo updatedb)
  • which [command] : path of the command that runs
  • whereis [command] : binary, source, and manual page locations
  • grep -rn "TODO" . : search inside file contents (see Text Processing)

Archives & Compression

tar bundles many files into one archive (a "tarball"); a compressor such as gzip then makes it smaller. They are usually combined in one step.

tar -czvf backup.tar.gz project/     # create a gzip-compressed archive
tar -xzvf backup.tar.gz              # extract it
tar -xzvf backup.tar.gz -C /tmp      # extract into another directory
tar -tzvf backup.tar.gz              # list contents without extracting
tar -cJvf backup.tar.xz project/     # xz compression (smaller, slower)
tar Flag Meaning
c / x / t create / extract / list
z / j / J gzip (.gz) / bzip2 (.bz2) / xz (.xz)
v verbose: list files as they are processed
f archive file name follows (always last)
Other Compression Tools
gzip file.txt            # compress to file.txt.gz (removes original)
gunzip file.txt.gz       # decompress
zip -r project.zip project/
unzip project.zip
unzip -l project.zip     # list contents
