Android Overview

  • Open-source OS based on Linux kernel, developed by Google
  • Designed for mobile devices (smartphones, tablets, TVs, wearables, IoT)
  • Provides middleware framework, runtime environment, application support
  • Development languages: Java, Kotlin, C/C++

Android Versions & API Levels

Every Android release has an API level, an integer that apps use to target behavior and check features at runtime (Build.VERSION.SDK_INT). Each release tightens privacy and security rules, which apply once an app raises its targetSdk.

Version API Year Key Changes for Developers
7.0 Nougat 24 2016 multi-window, APK signature scheme v2, Network Security Config; user-installed CAs no longer trusted by default
8.0 Oreo 26 2017 background execution limits, notification channels, Project Treble
9 Pie 28 2018 cleartext HTTP blocked by default, APK signature v3, BiometricPrompt
10 29 2019 scoped storage introduced, separate background location permission, system dark theme, gesture navigation
11 30 2020 scoped storage enforced, one-time permissions, package visibility (<queries>), auto-reset of unused permissions
12 / 12L 31 / 32 2021 Material You, explicit android:exported required, approximate location, PendingIntent mutability required
13 33 2022 notification runtime permission (POST_NOTIFICATIONS), photo picker, per-app languages, granular media permissions
14 34 2023 foreground service types required, Credential Manager (passkeys), implicit intents only reach exported components, apps targeting API below 23 cannot be installed
15 35 2024 edge-to-edge enforced, Private Space, 16 KB memory page size support
16 36 2025 adaptive layouts enforced on large screens, progress-centric Live Update notifications, Advanced Protection mode
  • Google Play Requirement : new apps and updates must target a recent API level, roughly within a year of the latest release, so apps keep moving to the newest rules.
  • Version Checks : guard newer APIs with if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) { ... } or use AndroidX libraries that handle it for you.

App Development & APK

Languages & Tooling
  • Kotlin : Google's preferred language since 2019. Java is still supported; C/C++ via the NDK for native/performance code.
  • Android Studio : the official IDE (built on IntelliJ), with the emulator, profiler, and layout editor.
  • Gradle : the build system; the Android Gradle Plugin (AGP) drives the build. SDK = libraries + build tools; NDK = native toolchain.
  • Jetpack : Google's recommended libraries (Compose for UI, Room, Navigation, WorkManager, DataStore).
Project Structure & Resources
  • AndroidManifest.xml : declares the app's package, components, permissions, and hardware features.
  • src/main/java : Kotlin/Java source code.
  • res/ : resources, referenced in code as R.type.name and compiled into the R class.
    • res/layout/ : XML UI layouts.
    • res/values/strings.xml : user-facing text (externalized for translation; res/values-fr/ etc. for other languages).
    • res/drawable/, res/mipmap/ : images and app icons.
  • assets/ : raw files bundled as-is. build.gradle : dependencies and build config.
Build Process
Kotlin / Java --(kotlinc / javac)--> .class --(D8 / R8: dex + shrink + obfuscate)--> classes.dex (DEX bytecode for ART) res/ --(AAPT2)--> compiled resources + resources.arsc --(Gradle package)--> unsigned APK --(zipalign + apksigner)--> signed APK -> install / Play
  • APK (Android Package) : the installable app file.
  • AAB (Android App Bundle) : the upload format for Google Play; Play generates per-device APKs from it.
APK Structure

An APK is a ZIP archive. Unzip it (or use apktool) to see:

  • AndroidManifest.xml : the manifest, stored as binary XML.
  • classes.dex : compiled app code as DEX bytecode (may be classes2.dex, ... for multidex).
  • resources.arsc : compiled resources (strings, styles).
  • res/ : non-compiled resources (images, raw XML). assets/ : bundled files.
  • lib/ : native .so libraries per ABI (arm64-v8a, x86_64).
  • META-INF/ : the signature and manifest of file hashes.
App Signing
  • Every APK must be signed; Android uses the signature to verify updates come from the same developer (an update must be signed with the same key).
  • Schemes : v1 (JAR signing), v2 (whole-file, Android 7+), v3 (adds key rotation, Android 9+), v4 (incremental install, Android 11+).
  • Play App Signing : Google holds the final signing key; you upload with an upload key.
ADB (Android Debug Bridge)

The main command-line tool for talking to a device or emulator over USB or Wi-Fi.

adb devices # list connected devices adb install app.apk # install an APK adb uninstall com.example.app adb shell # open a shell on the device adb logcat # live system/app logs adb pull /sdcard/file.txt . # copy from device adb push file.txt /sdcard/ # copy to device adb shell pm list packages # list installed packages adb shell am start -n com.example/.MainActivity # launch an activity adb shell dumpsys battery # query a system service
Reverse-Engineering Tools

Used for debugging, security review, and malware analysis (only on apps you are authorized to inspect).

  • aapt / aapt2 : inspect an APK's manifest, permissions, and resources.
  • apktool : decode an APK to smali and readable resources, and rebuild it.
  • jadx : decompile DEX back to readable Java.
  • apksigner / keytool : sign and verify APKs and certificates.
  • Frida / objection : dynamic instrumentation for runtime analysis.

Build Configuration

An app's build is defined in Gradle files (build.gradle.kts in Kotlin DSL). They set the SDK levels, the app's identity, build types, and dependencies.

SDK Levels
  • compileSdk : the API level the code is compiled against; decides which APIs are available at compile time.
  • minSdk : the oldest Android version the app installs on.
  • targetSdk : the version the app is tested against; Android applies that version's behavior changes to the app.
  • applicationId : the unique package name on the device and in Google Play; it can never change after publishing.
  • versionCode / versionName : an integer that must increase with every release, and the version string shown to users.
android { namespace = "com.example.app" compileSdk = 36 defaultConfig { applicationId = "com.example.app" minSdk = 24 targetSdk = 36 versionCode = 12 versionName = "1.4.0" } buildTypes { release { isMinifyEnabled = true // R8: shrink, optimize, obfuscate code isShrinkResources = true // remove unused resources proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro") signingConfig = signingConfigs.getByName("release") // defined in signingConfigs { } } debug { applicationIdSuffix = ".debug" // install debug and release side by side } } flavorDimensions += "tier" productFlavors { create("free") { dimension = "tier" } create("pro") { dimension = "tier"; applicationIdSuffix = ".pro" } } }
  • Build Variants : every build type combined with every flavor, e.g. freeDebug, proRelease; each can have its own source set (src/pro/).
  • R8 : removes unused code, renames classes and methods (obfuscation), and optimizes. Classes used through reflection need -keep rules in proguard-rules.pro, and the generated mapping.txt is needed to read obfuscated crash stack traces.
  • Version Catalog : gradle/libs.versions.toml keeps dependency versions in one place, referenced as libs.retrofit.
./gradlew assembleDebug # build a debug APK ./gradlew assembleRelease # build a signed release APK ./gradlew bundleRelease # build an AAB for Google Play ./gradlew test # local unit tests ./gradlew lint # static checks, including security rules ./gradlew :app:dependencies # dependency tree

System Architecture Layers

Linux Kernel (Base Layer)
  • Direct communication with hardware via drivers
  • Hardware abstraction, device drivers, power/memory/security management
  • Android-specific: Binder IPC driver for inter-process communication
  • Handles: security, memory, processes, networking, drivers (camera, display, Wi-Fi, Bluetooth, USB)
Hardware Abstraction Layer (HAL)
  • Sits above kernel
  • Provides standard interfaces/APIs between Android framework and hardware drivers
  • Translator between Java/Kotlin framework and C/C++ hardware drivers
  • Ensures apps don't need hardware-specific knowledge
Android Runtime & Native Libraries
  • Android Runtime (ART): Executes apps, replaced Dalvik VM from Android 5.0+
  • Uses JIT (Just-In-Time) and AOT (Ahead-Of-Time) compilation
  • Garbage collection, sandboxed process per app
  • Native C/C++ Libraries: SQLite, OpenGL ES, WebKit, SSL, Media Framework
Application Framework
  • High-level APIs and services for apps
  • Activity Manager: app lifecycles
  • Package Manager: installation, permissions
  • Resource Manager: layouts, strings, images
  • Notification Manager: system notifications
  • Location Manager: GPS
  • Telephony Manager: calls, SMS
  • View System: UI components
  • Content Providers: data sharing between apps
Applications Layer
  • System apps (Phone, Contacts, Camera)
  • User-installed apps
  • Built using Java/Kotlin, sometimes C/C++ for native parts

Application Components

The four core building blocks of an app. Each is declared in AndroidManifest.xml, and the system can start any of them. They are connected by Intents.

Component In one line
Activity a screen
Intent a request (to do something)
Broadcast an event message
Broadcast Receiver an event handler
Service background work
Content Provider a data-sharing interface
Activity
  • A single screen with a UI. An app is usually several activities (e.g. a list screen and a detail screen).
  • Lifecycle : onCreate -> onStart -> onResume -> (running) -> onPause -> onStop -> onDestroy (and onRestart when returning). Save state in onPause/onStop, since the system can kill a backgrounded app.
  • Modern apps often use a single activity with many Fragments or Jetpack Compose screens.
Intent

A messaging object used to request an action from a component: start an activity, start a service, or deliver a broadcast. It can carry data as extras.

  • Explicit Intent : names the exact target component. Used within your own app.
  • Implicit Intent : declares an action and lets the system pick a component that can handle it (e.g. open a URL, share text). Resolved against intent filters declared in the manifest.
  • PendingIntent : a token that lets another app (notifications, alarms) run an intent later as if it came from your app.
// Explicit: open a specific screen startActivity(Intent(this, DetailActivity::class.java).putExtra("id", 42)) // Implicit: let any browser open a URL startActivity(Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com")))
Service
  • Runs work without a UI, e.g. playing music or syncing.
  • Started service : runs until it stops itself. Bound service : runs while components are bound to it (client-server).
  • Foreground service : shows a persistent notification (music, navigation); required for long-running work on modern Android.
  • For deferrable background jobs, use WorkManager instead, because background execution is heavily restricted to save battery.
Broadcast Receiver
  • Responds to broadcast messages (events), from the system (battery low, connectivity change, boot completed) or from other apps.
  • Manifest-declared : can be triggered while the app is not running (limited for implicit broadcasts since Android 8). Context-registered : active only while the app runs.
  • A broadcast is the event message; the receiver is the handler that reacts to it.
Content Provider
  • A standard interface to share structured data between apps, accessed through content:// URIs via a ContentResolver.
  • System data like Contacts, Calendar, and MediaStore are exposed this way.
  • Access is guarded by permissions; exporting a provider carelessly is a common security risk.
App Sandbox
  • Each app gets a unique Linux UID and runs in its own process, isolated by the kernel and SELinux.
  • An app's private files are not readable by other apps. Sharing happens only through intents, content providers, or explicit permissions.
WebView
  • Android component for displaying web content inside apps
  • Mini browser engine (Chromium-based) embedded in Android
  • Packaged as: Android System WebView
  • API: android.webkit.WebView
  • Can load remote webpages, local HTML/JS files
  • JavaScript Interfaces: bridge between app code and web code
  • Security risks: JavaScript injection, insecure URL loading, XSS, phishing, MITM attacks

Manifest & Permissions

AndroidManifest.xml describes the app to the system: its package, components, the intents each component accepts, the permissions it needs, and app-wide security settings.

<manifest xmlns:android="http://schemas.android.com/apk/res/android"> <uses-permission android:name="android.permission.INTERNET" /> <uses-permission android:name="android.permission.CAMERA" /> <application android:label="@string/app_name" android:allowBackup="false" android:networkSecurityConfig="@xml/network_security_config"> <activity android:name=".MainActivity" android:exported="true"> <intent-filter> <action android:name="android.intent.action.MAIN" /> <category android:name="android.intent.category.LAUNCHER" /> </intent-filter> </activity> <!-- Verified App Link: https://example.com/product/... opens this screen --> <activity android:name=".ProductActivity" android:exported="true"> <intent-filter android:autoVerify="true"> <action android:name="android.intent.action.VIEW" /> <category android:name="android.intent.category.DEFAULT" /> <category android:name="android.intent.category.BROWSABLE" /> <data android:scheme="https" android:host="example.com" android:pathPrefix="/product" /> </intent-filter> </activity> <service android:name=".SyncService" android:exported="false" /> </application> </manifest>
Permission Protection Levels
Level Granted Examples
Normal automatically at install INTERNET, VIBRATE
Dangerous (runtime) by the user, through a prompt at runtime CAMERA, ACCESS_FINE_LOCATION, READ_CONTACTS, POST_NOTIFICATIONS
Signature only to apps signed with the same key as the app that defines it custom permissions between your own apps
Special (app ops) by the user on a Settings page SYSTEM_ALERT_WINDOW, MANAGE_EXTERNAL_STORAGE, SCHEDULE_EXACT_ALARM
Requesting a Runtime Permission
val requestCamera = registerForActivityResult(ActivityResultContracts.RequestPermission()) { granted -> if (granted) openCamera() else showRationale() } if (ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA) == PackageManager.PERMISSION_GRANTED) { openCamera() } else { requestCamera.launch(Manifest.permission.CAMERA) }
  • Ask in Context : request a permission when the user starts the feature that needs it, and explain why first if shouldShowRequestPermissionRationale() returns true.
  • Denials : after the user denies twice, the system stops showing the prompt; the app must degrade gracefully or send the user to Settings.
  • Avoid Permissions : system pickers (photo picker, file picker, contact picker) give access to chosen items without any permission.
Exported Components
  • android:exported : whether other apps can start a component. Required explicitly for components with intent filters since Android 12. Keep everything not meant for other apps set to false, or protect it with android:permission using a signature-level permission.
  • Validate Input : treat every intent extra as untrusted user input, since any app can send an intent to an exported component.
  • Package Visibility : since Android 11, apps see only some other installed apps by default; declare the ones you interact with in a <queries> element.
  • Deep Links : URLs that open a screen of the app are declared with intent filters too; see Deep Links & App Links.
Sharing Files (FileProvider)
  • Share files with other apps as content:// URIs from a FileProvider, never as file:// paths (blocked with FileUriExposedException since Android 7).
  • Grant access per intent with FLAG_GRANT_READ_URI_PERMISSION; the receiving app can read only that one file, and only temporarily.

Deep Links & App Links

A deep link is a URL that opens a specific screen inside an app instead of its home screen, e.g. a product page from an email or a QR code. Android matches the URL against the <intent-filter>s in the manifest (action VIEW, category BROWSABLE, and the <data> scheme, host, and path).

Type Example Behavior
Custom-scheme deep link myapp://product/42 not verified: any app can register the same scheme, and the user may see an app chooser
Web link https://example.com/product/42 without verification since Android 12, unverified web links open in the browser by default
Android App Link https://example.com/product/42 with autoVerify ownership verified through the website, so it opens the app directly with no chooser
Deferred deep link a link opened before the app is installed the user installs from Google Play, then lands on the linked content (via the Play Install Referrer or a linking service)
Declaring a Link
<activity android:name=".ProductActivity" android:exported="true"> <intent-filter android:autoVerify="true"> <action android:name="android.intent.action.VIEW" /> <category android:name="android.intent.category.DEFAULT" /> <category android:name="android.intent.category.BROWSABLE" /> <data android:scheme="https" android:host="example.com" android:pathPrefix="/product" /> </intent-filter> </activity>
Verifying an App Link (assetlinks.json)

The website proves it trusts the app by serving https://example.com/.well-known/assetlinks.json over HTTPS, with no redirects, listing the SHA-256 fingerprint of the app's signing certificate. With Play App Signing, use the fingerprint shown in the Play Console, not your local upload key.

[{ "relation": ["delegate_permission/common.handle_all_urls"], "target": { "namespace": "android_app", "package_name": "com.example.app", "sha256_cert_fingerprints": [ "14:6D:E9:83:C5:73:06:50:D8:EE:B9:95:2F:34:FC:64:16:A0:83:42:E6:1D:BE:A8:8A:04:96:B2:3F:CF:44:E5" ] } }]
Handling the Link
override fun onCreate(savedInstanceState: Bundle?) { super.onCreate(savedInstanceState) handleLink(intent) } override fun onNewIntent(intent: Intent) { // link opened while the activity already exists super.onNewIntent(intent) handleLink(intent) } private fun handleLink(intent: Intent) { val uri = intent.data ?: return // https://example.com/product/42 val id = uri.lastPathSegment?.toIntOrNull() ?: return // validate before using it showProduct(id) }
  • Navigation Component : declare links on destinations (<deepLink app:uri="https://example.com/product/{id}" /> in a nav graph, or navDeepLink in Compose) and the library parses arguments and builds the back stack.
  • Back Stack : a link opened from outside should leave a sensible back stack, so pressing Back goes to the app's parent screen, not straight out of the app.
Testing
adb shell am start -W -a android.intent.action.VIEW -d "https://example.com/product/42" com.example.app adb shell am start -W -a android.intent.action.VIEW -d "myapp://product/42" adb shell pm get-app-links com.example.app # verification state per domain (Android 12+) adb shell pm verify-app-links --re-verify com.example.app
Security
  • Link Hijacking : a malicious app can register the same custom scheme and receive the link, so never put tokens or secrets in custom-scheme links. Use verified App Links for anything sensitive.
  • Untrusted Input : every path segment and query parameter comes from whoever created the link; validate types and ranges before using them.
  • No Silent Actions : a link should only navigate. Require confirmation and authentication before payments, account changes, or password resets.
  • OAuth Redirects : native apps should receive OAuth redirects through App Links and always use PKCE (RFC 8252), since a hijacked redirect could otherwise leak the authorization code.
  • Intent Redirection : never launch an intent taken from link or extra data without checking where it points, or other apps can reach your unexported components through you.

Processes, Lifecycle & Background Work

Process Priority

When memory runs low, the low memory killer daemon (lmkd) ends processes from least to most important:

Priority Process State
Highest foreground: the activity the user is using, or a running foreground service
High visible: visible but not in focus (e.g. behind a dialog)
Medium service: running a started service
Lowest cached: in the background with nothing running; killed first
  • Process Death : a backgrounded app can be killed at any time. Keep UI state in a ViewModel (survives rotation) and SavedStateHandle / onSaveInstanceState (survives process death).
  • Configuration Changes : rotation, language, or dark-mode changes recreate the activity by default.
  • Main (UI) Thread : draws the UI and handles input. Blocking it causes an ANR (Application Not Responding) after about 5 seconds without responding to input; network calls on it throw NetworkOnMainThreadException.
Battery & Background Limits
  • Doze (Android 6) : when the device is idle and unplugged, network access and jobs are deferred into periodic maintenance windows.
  • App Standby Buckets (Android 9) : apps are ranked active, working set, frequent, rare, or restricted by how often they are used, which limits their jobs and alarms.
  • Background Execution Limits (Android 8) : background apps cannot start services freely or receive most implicit broadcasts.
Need Use
deferrable work that must eventually run (sync, upload) WorkManager (survives reboots; supports constraints like Wi-Fi or charging)
long-running work the user is aware of (music, navigation, calls) foreground service with a notification and a declared type (required on Android 14+)
work at an exact time (alarm clock, calendar) AlarmManager exact alarms (needs SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM)
work while the app is open Kotlin coroutines tied to a lifecycle scope
Coroutines
  • Dispatchers : Main (UI updates), IO (network, disk, database), Default (CPU-heavy work).
  • Scopes : viewModelScope and lifecycleScope cancel their coroutines automatically when the ViewModel or screen is destroyed (structured concurrency).
  • Flow : a cold stream of values; StateFlow holds the current UI state.
class ProfileViewModel(private val repo: UserRepository) : ViewModel() { private val _user = MutableStateFlow<User?>(null) val user: StateFlow<User?> = _user // observed by the UI fun load(id: Int) = viewModelScope.launch { _user.value = withContext(Dispatchers.IO) { repo.getUser(id) } // off the main thread } }

Notifications & Push

  • Notification Channels (Android 8+) : every notification belongs to a channel with an importance level; users can mute or change each channel in Settings, and the app cannot override their choice.
  • Runtime Permission (Android 13+) : apps must request POST_NOTIFICATIONS before posting notifications.
  • Tap Actions : a notification opens the app through a PendingIntent, which must be created with FLAG_IMMUTABLE (or explicitly mutable) on Android 12+.
  • Styles : heads-up, ongoing (required for foreground services), progress, messaging, expandable big-text and big-picture, and action buttons; Android 16 adds progress-centric Live Updates.
val channel = NotificationChannel("orders", "Order updates", NotificationManager.IMPORTANCE_DEFAULT) getSystemService(NotificationManager::class.java).createNotificationChannel(channel) val tap = PendingIntent.getActivity( this, 0, Intent(this, OrderActivity::class.java), PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT ) val notification = NotificationCompat.Builder(this, "orders") .setSmallIcon(R.drawable.ic_notification) .setContentTitle("Order shipped") .setContentText("Your order #1042 is on the way") .setContentIntent(tap) .setAutoCancel(true) // dismiss when tapped .build() NotificationManagerCompat.from(this).notify(1042, notification) // after POST_NOTIFICATIONS is granted
Push Notifications (FCM)
  • Token : each app install gets a registration token, which the app sends to your server so it can target that device.
  • Notification vs Data Messages : notification messages are displayed by the system automatically when the app is in the background; data messages are delivered to FirebaseMessagingService.onMessageReceived() for the app to handle.
  • Priority : high-priority messages can wake a dozing device; use them only for time-sensitive, user-visible content, or the system may deprioritize the app.
  • Security : treat push payloads as untrusted and fetch sensitive data from your server after the message arrives, rather than putting it in the payload.

App Architecture & Jetpack

Google's recommended architecture separates an app into layers, with data flowing in one direction: state flows down to the UI and events flow up from it.

UI layer Activity / Fragment / Composable <-> ViewModel (holds UI state) | Domain layer use cases (optional business logic) | v Data layer Repository -> Room (local database) + Retrofit (network API)
  • MVVM : the View observes the ViewModel's state and sends user events to it; the ViewModel never references views, so it is testable and survives rotation.
  • Repository : the single source of truth for a type of data, deciding between cache, database, and network.
  • Dependency Injection : Hilt (built on Dagger) or Koin create and supply dependencies, so classes do not construct their own.
UI Toolkits
  • Views (XML) : the classic toolkit: XML layouts, ConstraintLayout, RecyclerView for lists, Fragments for reusable screen parts.
  • Jetpack Compose : the modern declarative toolkit: UI is written as @Composable Kotlin functions that re-run (recompose) when their state changes. Recommended for new apps.
@Composable fun Counter(name: String) { var count by remember { mutableStateOf(0) } // state that survives recomposition Column(Modifier.padding(16.dp)) { Text("Hello, $name") Button(onClick = { count++ }) { Text("Clicked $count times") } } }
Key Jetpack Libraries
Library Purpose
Lifecycle / ViewModel lifecycle-aware components and UI state holders
Navigation moving between screens, back stack, deep links
Room type-safe SQLite database with compile-time checked queries
DataStore key-value or typed storage, replacing SharedPreferences
WorkManager guaranteed background work
Paging loading large lists page by page
CameraX camera access that works consistently across devices
Hilt dependency injection

Networking & Network Security

  • Permission : network access needs INTERNET (a normal permission, granted at install).
  • OkHttp : the standard HTTP client (connection pooling, HTTP/2, interceptors for logging and auth headers).
  • Retrofit : builds a type-safe REST client from an interface, on top of OkHttp; Ktor client is a Kotlin-first alternative.
interface ApiService { @GET("users/{id}") suspend fun getUser(@Path("id") id: Int): User } val api: ApiService = Retrofit.Builder() .baseUrl("https://api.example.com/") .addConverterFactory(GsonConverterFactory.create()) // or Moshi / kotlinx.serialization .build() .create(ApiService::class.java)
Network Security Configuration

An XML file (res/xml/network_security_config.xml, referenced from the manifest) controls which connections and certificates an app trusts, without code changes.

  • Cleartext : plain HTTP is blocked by default for apps targeting Android 9 (API 28) or higher.
  • Trusted CAs : apps targeting Android 7 (API 24) or higher trust only system CAs by default, not certificates the user installs. This is why HTTPS-inspecting proxies need a debug-only override.
  • Certificate Pinning : restricts a domain to specific public keys. Always include a backup pin and an expiration date, or a key rotation can lock every user out of the app.
<network-security-config> <base-config cleartextTrafficPermitted="false"> <trust-anchors> <certificates src="system" /> </trust-anchors> </base-config> <domain-config> <domain includeSubdomains="true">api.example.com</domain> <pin-set expiration="2027-01-01"> <pin digest="SHA-256">7HIpactkIAq2Y49orFOOQKurWxmmSFZhBCoQYcRhJ3Y=</pin> <pin digest="SHA-256">fwza0LRMXouZHRC8Ei+4PyuldPDcf3UKgO/04cDM1oE=</pin> <!-- backup key --> </pin-set> </domain-config> <!-- Applies only to debuggable builds, e.g. to inspect traffic with a debugging proxy --> <debug-overrides> <trust-anchors> <certificates src="user" /> </trust-anchors> </debug-overrides> </network-security-config>

The pin values above are the placeholder examples from Android's documentation; real pins are the Base64 SHA-256 hash of your server's public key.

Data Storage & Keystore

Each app stores its private data in its own sandbox folder, /data/data/<package>/ (also /data/user/0/<package>/), which other apps cannot read.

Path (inside the app sandbox) Contents
files/ internal storage files
databases/ SQLite database files
shared_prefs/ SharedPreferences XML files
cache/ temporary cache (the system may clear it)
Storage Options
  • SharedPreferences : small key-value pairs (settings, flags) saved as XML. DataStore is the modern Jetpack replacement.
  • Internal Storage : private files in the app sandbox; removed when the app is uninstalled.
  • External Storage : shared storage (/sdcard). Since Android 10/11, scoped storage limits apps to their own media and the MediaStore / Storage Access Framework for the rest.
  • SQLite : the built-in on-device relational database (see below).
  • Room : the Jetpack ORM over SQLite; compile-time checked queries, less boilerplate. Recommended for structured data.
SQLite
  • A lightweight, serverless, file-based relational database built into Android; the standard for structured local data.
  • Each database is a single file in databases/. Accessed with SQL; apps usually use Room on top rather than raw SQL.
  • Security note : a plain SQLite file is not encrypted. Anyone with the file (e.g. on a rooted device or via backup) can read it. Use encryption (SQLCipher, or encrypt via the Keystore) for sensitive data.
# Inspect an app's database on a device (debuggable app / emulator) adb shell run-as com.example.app ls databases/ adb shell "run-as com.example.app sqlite3 databases/app.db '.tables'"
Android Keystore

The Keystore system stores cryptographic keys in a container that is hard to extract from the device. Keys are generated and used inside secure hardware, so the key material never enters the app's memory.

  • Hardware-backed : keys live in the TEE (Trusted Execution Environment) or a dedicated StrongBox secure element; they cannot be exported, only used.
  • Access control : a key can require user authentication (biometric / PIN) before each use, or be invalidated if the lock screen is removed.
  • The app asks the Keystore to encrypt, decrypt, or sign; it never sees the raw key.
Secure Data Storage
  • EncryptedSharedPreferences : SharedPreferences with keys and values encrypted using a Keystore-backed key (Jetpack Security).
  • EncryptedFile : the same idea for files.
  • Rule of thumb : keep secrets out of plain SharedPreferences, logs, and external storage. Hard-coded keys in the APK can be extracted by decompiling (see App Development & APK).

App Security Checklist

The OWASP MASVS (Mobile Application Security Verification Standard) defines what a secure mobile app must do; the MASTG (testing guide) explains how to verify each requirement.

MASVS Category Covers
MASVS-STORAGE sensitive data stored on the device
MASVS-CRYPTO correct use of cryptography and keys
MASVS-AUTH authentication and session handling
MASVS-NETWORK secure network communication
MASVS-PLATFORM safe use of platform features (IPC, WebViews, permissions)
MASVS-CODE code quality, dependencies, and updates
MASVS-RESILIENCE resistance to tampering and reverse engineering
MASVS-PRIVACY user privacy and data minimization
Hardening Checklist
  • No Secrets in the APK : API keys and passwords in code or strings.xml can be extracted by decompiling. Keep them on a backend, and protect on-device keys with the Android Keystore.
  • Release Builds : never ship a debuggable build; make sure android:debuggable is not set to true.
  • Backups : set android:allowBackup="false", or exclude sensitive files with dataExtractionRules (Android 12+).
  • Components : set android:exported explicitly, protect exported components with signature permissions, and validate every intent extra and deep-link parameter.
  • PendingIntents : use FLAG_IMMUTABLE unless the receiver truly needs to modify the intent.
  • WebViews : keep JavaScript off unless needed, load only HTTPS content you control, never expose addJavascriptInterface to untrusted pages, and keep file access disabled.
  • Content Providers : keep them unexported or permission-protected, and pass user input through selectionArgs instead of building SQL strings.
  • Network : HTTPS only, no cleartext exceptions in release, and certificate pinning for high-risk apps.
  • Logging : no tokens or personal data in logs; strip debug logging from release builds.
  • Sensitive Screens : FLAG_SECURE blocks screenshots, screen recording, and the preview in the recent-apps screen.
  • Integrity : check Play Integrity API verdicts on your server, never only on the device, since on-device checks can be bypassed.
Review Tools (for your own apps)
  • Android Lint : built-in security checks (./gradlew lint).
  • MobSF : automated static and dynamic analysis of an APK.
  • jadx / apktool : inspect what your release build actually exposes (see App Development & APK).

File System Structure

  • / : Root Directory - Essential Folders:
  • /system : Core Android OS files (read-only)
    • /system/app : Pre-installed system apps
    • /system/framework : Android frameworks (.jar files)
    • /system/lib, /system/lib64 : Shared libraries (.so files)
    • /system/bin : Core binaries (sh, toolbox)
  • /vendor : Device-specific files (drivers, firmware, HAL)
  • /boot : Kernel + ramdisk
  • /recovery : Boot partition for system recovery
  • /data : User data (writable)
    • /data/app : Installed apps (APK files)
    • /data/data/<package_name> : App-specific data (databases, cache, prefs)
    • /data/dalvik-cache : Compiled code cache
  • /cache : Temporary data, OTA updates
  • /sdcard or /storage/emulated/0 : User files (media, downloads)
  • /dev : Device nodes for hardware
  • /proc : Runtime kernel/system info
  • /etc : Config files

Boot Process & Low-Level Components

Bootloader
  • First program on device power-on
  • Initializes hardware, verifies system integrity, loads OS kernel
  • Decides boot mode: Android OS, Recovery, or Fastboot/Download Mode
  • Locked: secure, stock firmware only
  • Unlocked: allows custom ROMs, kernels, recovery
Fastboot / Download Mode
  • Diagnostic and flashing interface before Android boots
  • Communicates via ADB/Fastboot commands
  • Allows: unlock/lock bootloader, flash system images, repair bricked device
  • Samsung uses Download Mode (Odin) instead
Recovery
  • Separate lightweight runtime on /recovery partition
  • Stock Recovery: limited, official only
  • Custom Recovery (TWRP): advanced flashing, backups, root access
  • System maintenance: factory reset, OTA updates, custom ROM flashing
Zygote
  • A special daemon process, started early by init, that serves as the parent of all app processes
  • Loads and initializes Android Runtime (ART/Dalvik), core libraries and system classes once, then forks for new apps
  • Without Zygote, every app would initialize the ART runtime separately -> resulting in slow launches and high memory usage -> whereas with Zygote, a single preloaded runtime is forked quickly -> enabling fast app launches and efficient memory use
  • Forking model: fast app launches, efficient memory use
  • Security: SELinux and sandboxing apply immediately on fork
BusyBox
  • Lightweight package with Unix/Linux utilities in single executable
  • Often called the "Swiss Army Knife of Embedded Linux"
  • Designed for systems with limited resources (Android, routers, IoT devices)
  • Android lacks many standard Linux utilities by default, but BusyBox fills the gap by providing a wide set of Linux commands in a compact form.
  • Combines many commands (ls, cat, grep, find, ifconfig) into one binary
  • Enables: advanced file operations (find, cp, mv), network utilities (ifconfig, netstat, ping), system admin commands (top, ps), custom shell scripts
  • Essential for rooting, custom ROMs, pentesting
  • Common in custom recoveries (TWRP) and rooted environments

Android Security Core

Android Verified Boot (AVB)
  • Ensures device boots only trusted software by verifying the integrity of each stage of the boot process
  • Evolution of dm-verity (introduced Android 4.4), standardized as AVB 2.0 in Android 7.0+
  • Root of Trust: starts with bootloader (signed by the device manufacturer)
  • Chain of Trust: each stage verifies the integrity and authenticity of the next stage using cryptographic signatures (bootloader -> kernel -> system -> vendor)
  • Rollback Protection: prevents downgrading to vulnerable OS versions
  • Prevents persistent malware, rootkits, system partition tampering
  • Modified blocks fail verification -> device refuses to boot or shows warning
DM-Verity (Device-Mapper Verity)
  • Kernel feature for verified boot (AVB implementation)
  • Block-level integrity checker for /system, /vendor partitions
  • Uses hash tree (Merkle tree) of cryptographic checksums in boot image
  • Each block checked against expected hash
  • Mismatch -> device refuses to boot (bootloop) or replaces block with zeros
    • On boot, the kernel initiates dm-verity, which verifies each block of the verified partition by hashing it and comparing it against a precomputed hash tree.
    • The root hash of that tree is signed by the manufacturer and verified during Verified Boot.
    • If corruption is detected, the device either fails to boot (boot loop) or replaces bad data with zeros (the device runs, but with corrupted or missing functionality).
  • Prevents: malware persistence, system file tampering, backdoors
  • Obstacle for root/custom ROMs: must disable dm-verity for modifications
  • Rooting with system modifications (e.g., SuperSU) breaks dm-verity by altering the verified partition, causing hash mismatches that lead to boot loops or zeroed data
  • Magisk achieves systemless root by keeping /system intact, modifying /boot
SELinux (Security-Enhanced Linux)
  • Kernel-level security module, enforces Mandatory Access Control (MAC)
  • Introduced in Android 4.3 (2013) and default enforcing since Android 5.0 (2014)
  • Unlike traditional Linux Discretionary Access Control (DAC), where the owner of a resource decides who can access it, SELinux enforces centralized, mandatory rules that define exactly which processes can access which resources.
  • Every process, file, resource has security context (label)
  • Policies define allowed actions between contexts
  • Even root apps must respect SELinux policies (in enforcing mode)
  • Prevents root malware from complete takeover
  • Confines compromised apps within defined boundaries
  • Even if an app like untrusted_app is compromised, SELinux confines it -> blocking access to sensitive areas like /data/system/ and kernel memory
  • Modes: Permissive (logs violations), Enforcing (blocks violations)

Google Ecosystem

Google Mobile Services (GMS)
  • Proprietary Google apps & APIs on top of Android
  • Includes: Play Store, Play Services, Firebase, FCM, Play Integrity API, Maps, Gmail, YouTube
Services for Developers
  • Play Integrity API : returns signed verdicts about whether the request comes from your genuine app, installed from Google Play, on a genuine certified device. It replaced the SafetyNet Attestation API. Verify the verdict on your server.
  • Firebase Cloud Messaging (FCM) : push messages to devices, delivered through Google Play services' single persistent connection to save battery.
  • Play Console : internal, closed, and open testing tracks, staged rollouts to a percentage of users, crash and ANR reports (Android vitals), and pre-launch testing.
  • Devices without GMS : AOSP-based devices without Google services (e.g. Huawei devices use HMS) need alternatives for push, maps, and integrity checks.

System Images & ROMs

Generic System Image (GSI)
  • Pure AOSP implementation for Project Treble devices (Android 8.0+)
  • A system image with unmodified AOSP code (no OEM customizations)
  • Used for: testing, pentesting, device validation
System Updates & Modularity
  • Project Treble (Android 8) : a stable vendor interface separates the Android framework from device-specific vendor code (HALs), so the OS can be updated without the chip vendor rebuilding everything. It is also what makes GSIs possible.
  • Project Mainline (Android 10) : core system components (media codecs, DNS resolver, permission controller, and more) ship as APEX and APK modules updated through Google Play, between full OS updates.
  • A/B (Seamless) Updates : partitions come in two slots (_a and _b); the update installs to the inactive slot while the phone is in use, and a failed update rolls back automatically. Virtual A/B (Android 11) uses snapshots to save space.
  • Dynamic Partitions (Android 10) : system, vendor, and product live as resizable logical partitions inside one super partition.
  • Generic Kernel Image (GKI) : since Android 12, devices use a common Google-maintained kernel, with vendor-specific code moved into loadable modules.
  • Security Patch Level : Google publishes a monthly Android Security Bulletin, and devices report the patch level they include (Settings > About phone).

Root

Rooting
  • Gaining privileged (root/administrator) access to Android OS
  • Unlocks root user (superuser) account (UID 0)
  • Usually requires unlocked bootloader first
  • Root vs Bootloader Unlock: bootloader unlock allows flashing, root gives admin control
  • Allows: modify system files, remove bloatware, install custom ROMs/kernels, system access apps, performance tweaks
  • Risks: security vulnerabilities, malicious apps could gain full control, warranty void, OTA updates blocked, bricking, SafetyNet/Play Integrity fail
Root Binary (su)
  • Root account disabled by default in Android
  • No su binary in /system/bin or /system/xbin
  • Apps run sandboxed with own UID, managed by Zygote + SELinux
  • Rooting installs su binary (switch user) in system
  • su binary lets processes switch to UID 0 (root)
  • Superuser Manager (SuperSU/Magisk) intercepts su calls, prompts user for permission
Rooting Methods
System Modifying Root (Older)
  • Tools like SuperSU modified /system partition
  • Inserted su binary directly in system
  • Risks: permanently changed system, broke OTA updates, easily detected
Systemless Root - Magisk (Modern)
  • Modern systemless rooting framework by topjohnwu
  • Systemless Root: patches boot image (boot.img), not /system and loads root at boot
  • Provides: root access (su) and modules system
  • Magisk Modules: plugins for features (ad-block, theming, performance)
  • Zygisk: runs inside Zygote for finer control
  • DenyList: hide modifications/root from specific apps
  • Supports OTA updates, minimal system modification, and easy to undo
  • Steps: unlock bootloader -> extract boot.img -> patch with Magisk -> flash patched boot.img
