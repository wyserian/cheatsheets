Windows

Microsoft Windows is a family of proprietary, closed-source operating systems first released in 1985. Modern Windows (10, 11, and Server) is built on the Windows NT architecture, a clean design from 1993 that replaced the old MS-DOS base. NT was designed to be secure, multi-user, portable across processors, and fully 32/64-bit.

Key Characteristics -
  • Hybrid Kernel : A middle ground between monolithic and microkernel designs. Core services run in kernel mode for speed, but the design is more modular than classic UNIX.
  • Backward Compatibility : A strong focus on running old software on new versions, a major reason for Windows' dominance on the desktop.
  • GUI-First : Built around a graphical interface, with the command line (CMD, PowerShell) as a secondary interface.
  • Driver Model : Hardware vendors ship signed drivers (.sys) that load into the kernel.
  • Win32 API : The long-standing native programming interface; newer apps may use WinRT / the Windows App SDK.
Editions & Lines -
  • Client : Windows 10, Windows 11 (Home, Pro, Enterprise, Education).
  • Server : Windows Server 2019 / 2022 / 2025, used for Active Directory, file, web, and database services.
  • Specialized : Windows IoT (embedded devices), Windows on ARM.

The NT version number differs from the marketing name: Windows 10 and 11 are both NT 10.0 internally. Check it with winver.

Architecture

Windows separates code into two privilege levels, like Linux. User mode runs applications with restricted access; kernel mode runs the core OS with full hardware access. Crossing between them happens through system calls.

+==============================================================+
|  USER MODE                                                   |
|  Apps  |  System Processes      |  Subsystems               |
|        |  (winlogon, services)  |  (Win32, WSL)             |
|  ----------------------------------------------------------  |
|  Subsystem DLLs:  kernel32.dll  user32.dll  advapi32.dll    |
|  ntdll.dll  (gateway to kernel: system calls)               |
+==============================================================+  <- syscall boundary
|  KERNEL MODE                                                 |
|  Executive  (I/O, memory, process, security, IPC managers)  |
|  Kernel     (scheduling, interrupts)                         |
|  HAL  (Hardware Abstraction Layer)  |  Drivers (.sys)        |
+==============================================================+
|  Hardware                                                    |
+==============================================================+
Core Components -
  • HAL (hal.dll) : Hardware Abstraction Layer. Hides CPU/motherboard differences so the kernel is portable.
  • Kernel (ntoskrnl.exe) : The NT kernel: thread scheduling, interrupts, and low-level synchronization.
  • Executive : The upper kernel-mode layer with the managers for memory, processes, I/O, and security (the Security Reference Monitor).
  • ntdll.dll : The lowest user-mode DLL; turns documented API calls into system calls (syscall instruction) into the kernel.
  • Subsystem DLLs : kernel32.dll (core Win32), user32.dll (windows, input), gdi32.dll (graphics), advapi32.dll (registry, security).
  • Win32 Subsystem (csrss.exe) : Client/Server Runtime, manages console windows and processes for the Win32 environment.
Processes, Threads & Services -
  • Process : A running program with its own virtual memory and one or more threads. Identified by a PID.
  • Thread : The unit the scheduler runs. A process has at least one.
  • Service : A background process (the Windows equivalent of a daemon), managed by the Service Control Manager (services.msc, sc.exe). Many run inside shared svchost.exe host processes.
  • Session : Session 0 is reserved for services; interactive users log on to session 1 and above (session isolation).
Key System Processes -
Process Role
System (PID 4) host for kernel-mode threads
smss.exe Session Manager, the first user-mode process
csrss.exe Win32 subsystem
wininit.exe starts background services in session 0
winlogon.exe handles interactive logon
lsass.exe Local Security Authority: authentication and tokens
services.exe Service Control Manager
explorer.exe desktop, taskbar, and file browser shell

Boot Process

Power On -> UEFI/BIOS firmware -> Boot Manager (bootmgfw.efi)
   -> Windows Loader (winload.efi) -> Kernel (ntoskrnl.exe) + HAL + drivers
      -> Session Manager (smss.exe) -> wininit.exe + winlogon.exe
         -> Services + Logon UI -> Desktop
  • 1. Firmware (UEFI/BIOS) : Runs POST, then hands off to the boot manager. UEFI is the modern standard and is required for Secure Boot.
  • 2. Windows Boot Manager (bootmgfw.efi) : Reads the BCD (Boot Configuration Data) store and shows the OS menu. Replaces the old boot.ini.
  • 3. Windows Loader (winload.efi) : Loads the kernel, the HAL, and boot-critical drivers into memory.
  • 4. Kernel Init : The kernel initializes the Executive, starts remaining drivers, and launches the Session Manager.
  • 5. smss.exe : Sets up the environment, paging file, and sessions, then starts csrss.exe and wininit.exe.
  • 6. wininit.exe : Starts the Service Control Manager (services.exe), the Local Security Authority (lsass.exe), and the Local Session Manager.
  • 7. winlogon.exe : Shows the logon UI (LogonUI), authenticates the user through LSASS, and starts explorer.exe.
BCD & Boot Tools -
bcdedit                       :: view the boot configuration store
bcdedit /set {current} safeboot minimal  :: next boot into Safe Mode
msconfig                      :: System Configuration (boot options GUI)
bootrec /rebuildbcd           :: repair BCD from recovery environment

If boot fails repeatedly, Windows loads WinRE (Windows Recovery Environment) for Startup Repair, System Restore, and a command prompt.

Secure Boot & TPM

• Secure Boot :

Secure Boot is a UEFI feature that ensures only software signed by a trusted key runs during boot, blocking bootkits and rootkits that load before the OS. The firmware verifies the signature of each boot component before running it, forming a chain of trust from the firmware up to the kernel.

  • Keys : PK (Platform Key, owned by the OEM), KEK (Key Exchange Keys), and the db / dbx databases of allowed and revoked signatures.
  • Chain of Trust : Firmware verifies the Boot Manager, which verifies the Loader, which verifies the kernel and its drivers.
  • Requirement : Secure Boot (plus TPM 2.0) is a formal requirement for Windows 11.
• TPM (Trusted Platform Module) :

The TPM is a dedicated secure hardware chip (or firmware equivalent, fTPM) that stores cryptographic keys and performs crypto operations in isolation from the main CPU and OS. Keys generated inside the TPM never leave it in plaintext.

  • PCRs (Platform Configuration Registers) : Store measurements (hashes) of the boot components. Their values change if boot code is tampered with.
  • Sealing : Data can be encrypted (sealed) so it only decrypts when the PCRs match a known-good boot state. BitLocker uses this to release its key only if the boot chain is intact.
  • Attestation : The TPM can produce signed proof of the machine's boot state for a remote server.
  • Measured Boot : Each boot stage measures the next into the TPM before running it, creating a verifiable log.
• BitLocker :

BitLocker is Windows' full-volume encryption. With a TPM, the decryption key is sealed to the boot state, so the drive stays locked if moved to another machine or if the boot chain is altered.

tpm.msc                          :: TPM management console
Get-Tpm                          # PowerShell: TPM status
manage-bde -status               :: BitLocker status of all volumes
manage-bde -protectors -get C:   :: show recovery key info
Confirm-SecureBootUEFI           # PowerShell: is Secure Boot on?

File System & Paths

Unlike Linux's single tree, Windows gives each volume a drive letter (C:, D:). Paths use backslashes (\), and file names are case-insensitive (but case-preserving).

Path Types -
  • Absolute : C:\Users\Rahul\file.txt (drive + full path).
  • Relative : docs\file.txt, ..\backup.
  • UNC (network) : \\server\share\file.txt for files on another machine.
  • Extended-length : \\?\C:\very\long\path bypasses the old 260-character MAX_PATH limit.
  • Device : \\.\PhysicalDrive0, \\.\C: for raw device access.
Key Folders -
Path Contents
C:\Windows the OS itself (%SystemRoot%)
C:\Windows\System32 core DLLs and executables (64-bit, despite the name)
C:\Windows\SysWOW64 32-bit system files on 64-bit Windows
C:\Program Files 64-bit installed applications
C:\Program Files (x86) 32-bit installed applications
C:\Users\[name] user profile folder (%USERPROFILE%)
C:\ProgramData app data shared by all users (hidden)
%AppData% per-user roaming app data (...\AppData\Roaming)
%LocalAppData% per-user local (non-roaming) app data
%TEMP% temporary files
Environment Variables -

Referenced as %NAME% in CMD and $env:NAME in PowerShell.

  • %SystemRoot% / %windir% : C:\Windows
  • %USERPROFILE% : C:\Users\[name]
  • %PATH% : folders searched for executables (semicolon-separated)
  • %COMPUTERNAME%, %USERNAME%, %USERDOMAIN%

NTFS

NTFS (New Technology File System) is the default Windows file system since Windows NT. It is a journaling file system with permissions, encryption, compression, and large-volume support.

Key Features -
  • MFT (Master File Table) : A database with one record per file, holding its metadata and (for small files) the data itself.
  • Journaling : A transaction log ($LogFile) lets NTFS recover a consistent state after a crash.
  • ACL Permissions : Fine-grained per-user and per-group access control (see below), far richer than Linux's rwx.
  • Alternate Data Streams (ADS) : A file can hold extra hidden streams of data (file.txt:hidden). The Zone.Identifier stream marks files downloaded from the internet (Mark of the Web).
  • EFS (Encrypting File System) : Per-file transparent encryption tied to the user's certificate.
  • Compression & Quotas : Transparent per-folder compression and per-user disk quotas.
  • Hard Links, Junctions & Symlinks : Multiple names for one file, and directory redirections (mklink).
  • VSS (Volume Shadow Copy) : Point-in-time snapshots used for backups and System Restore.
NTFS Permissions (ACLs) -

Each file/folder has a DACL (Discretionary Access Control List) made of ACEs (Access Control Entries) that allow or deny a trustee specific rights. Permissions are inherited from the parent folder by default.

Permission Meaning
Full Control everything, including changing permissions and ownership
Modify read, write, and delete
Read & Execute read and run programs
Read view contents and attributes
Write create files and write data 
icacls C:\data                       :: view a file/folder ACL
icacls C:\data /grant Rahul:(OI)(CI)M :: grant Modify, inherited by children
icacls C:\data /remove Guest          :: remove a user's entries
takeown /f C:\data /r                 :: take ownership recursively
dir /r                                :: show alternate data streams
mklink /D Link Target                 :: directory symbolic link
mklink /H hard.txt file.txt           :: hard link
compact /c /s file.txt                :: NTFS compression
cipher /e file.txt                    :: EFS encryption
Other Windows File Systems -
  • FAT32 : Old, simple; 4 GB max file size. Still used for small USB drives and UEFI system partitions.
  • exFAT : FAT without the size limit, for large USB drives and SD cards shared across OSes.
  • ReFS (Resilient File System) : Server-focused, with automatic integrity checks and self-healing on Storage Spaces.

Registry

The Registry is a central hierarchical database for OS and application configuration, the Windows equivalent of Linux's scattered /etc files. It is edited with regedit or the reg command, and read/written through the advapi32.dll APIs.

Structure -
  • Keys : Folders in the tree (can contain subkeys).
  • Values : The data inside a key, each with a name, type, and data.
  • Value Types : REG_SZ (string), REG_DWORD / REG_QWORD (32/64-bit number), REG_BINARY, REG_MULTI_SZ, REG_EXPAND_SZ.
  • Hives : The physical files backing the registry, stored in C:\Windows\System32\config (SYSTEM, SOFTWARE, SAM, SECURITY) and the per-user NTUSER.DAT.
Root Keys (Hives) -
Root Key Contents
HKLM (HKEY_LOCAL_MACHINE) system-wide settings: hardware, drivers, services, installed software
HKCU (HKEY_CURRENT_USER) settings for the user currently logged on
HKU (HKEY_USERS) settings for all loaded user profiles
HKCR (HKEY_CLASSES_ROOT) file associations and COM registrations (a merged view)
HKCC (HKEY_CURRENT_CONFIG) current hardware profile (a view into HKLM)
Notable Keys -
  • Autostart (common malware persistence) : HKLM\...\CurrentVersion\Run and HKCU\...\CurrentVersion\Run list programs that launch at logon.
  • Services : HKLM\SYSTEM\CurrentControlSet\Services.
  • Installed software : HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall.
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion /v ProgramFilesDir
reg add  HKCU\Software\MyApp /v Theme /t REG_SZ /d Dark
reg delete HKCU\Software\MyApp /v Theme /f
reg export HKCU\Software\MyApp backup.reg
reg import backup.reg

# PowerShell treats the registry as a drive:
Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion" | Select ProductName
Set-ItemProperty "HKCU:\Software\MyApp" -Name Theme -Value Dark

Services & Scheduled Tasks

• Services :

A service is a background process (like a Linux daemon) managed by the Service Control Manager (SCM). Services can start at boot before any user logs on. They are defined under HKLM\SYSTEM\CurrentControlSet\Services and are a top target for persistence and privilege escalation, so auditors review them closely.

Start Types -
  • Automatic : starts at boot (optionally "Automatic (Delayed Start)").
  • Manual : starts on demand or when triggered.
  • Disabled : cannot start.
Service Accounts -
  • LocalSystem : highest local privilege; avoid unless required.
  • LocalService / NetworkService : low-privilege built-in accounts (NetworkService uses the machine account on the network).
  • Managed Service Account (MSA/gMSA) : domain accounts with automatically rotated passwords; preferred for domain services.
sc query                              :: list running services
sc qc [service]                       :: config (binary path, account, start type)
sc query [service]                    :: current state
sc config [service] start= disabled   :: change start type (note the space after =)
net start / net stop [service]        :: start / stop

# PowerShell (see the PowerShell cheatsheet for more)
Get-Service | Where-Object Status -eq Running
Get-CimInstance Win32_Service | Select Name, StartName, PathName, StartMode
Common Audit Findings -
  • Unquoted Service Path : a service binary path with spaces and no quotes (e.g. C:\Program Files\My App\svc.exe) can let a planted C:\Program.exe run as the service account.
  • Weak Service Permissions : if a low-privileged user can reconfigure a service (SERVICE_CHANGE_CONFIG) or replace its binary, they can run code as SYSTEM. Check with Sysinternals accesschk -uwcqv.
  • Insecure Registry / Binary ACLs : writable service keys or executables.
• Scheduled Tasks :

The Task Scheduler runs programs on triggers: a time, at logon/boot, on an event, or on idle. Tasks are stored in C:\Windows\System32\Tasks (XML) and under the registry. Like services, they are a common persistence mechanism.

schtasks /query /fo LIST /v             :: list all tasks (verbose)
schtasks /create /tn Backup /tr C:\b.bat /sc daily /st 02:00
schtasks /run /tn Backup                :: run now
schtasks /delete /tn Backup /f
taskschd.msc                            :: Task Scheduler GUI

# PowerShell
Get-ScheduledTask | Where-Object State -ne Disabled
Get-ScheduledTask Backup | Get-ScheduledTaskInfo   # last/next run

Autostart locations (services, tasks, Run keys, startup folders) are best reviewed together with Sysinternals Autoruns (see Processes, DLLs & Signing).

Processes, DLLs & Signing

• Executables & the PE Format :

Windows programs and libraries use the PE (Portable Executable) format: .exe, .dll, .sys (drivers). Understanding its layout matters for debugging, malware analysis, and auditing.

  • DOS Header : starts with MZ; holds a stub and a pointer to the PE header.
  • PE Header : target architecture, number of sections, entry point, subsystem (GUI/console).
  • Sections : .text (code), .data (variables), .rdata (read-only + imports), .rsrc (resources: icons, manifest, version), .reloc (relocations).
  • Imports (IAT) : the functions and DLLs the program depends on; Exports are what a DLL provides.
• DLLs & Search Order :

A DLL (Dynamic Link Library) is shared code loaded at runtime. When a program loads a DLL by name, Windows searches directories in a set order. With the default SafeDllSearchMode on, the order is roughly:

1. The application's own directory
2. The system directory (C:\Windows\System32)
3. The 16-bit system directory
4. The Windows directory
5. The current working directory (CWD)
6. Directories listed in the PATH environment variable
  • DLL Hijacking (Search-Order Hijacking) : if a program loads a DLL that is not in a protected location, an attacker who can write to an earlier directory in the search order can drop a malicious DLL that gets loaded instead. A frequent privilege-escalation and persistence finding.
  • Phantom DLL : the program tries to load a DLL that does not exist, so any planted one is used.
  • KnownDLLs : core system DLLs listed under HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs are always loaded from System32, which protects them from hijacking.
  • DLL Side-Loading : a signed, trusted executable is used to load a malicious DLL placed beside it.
• Code Signing (Authenticode) :

Authenticode lets publishers sign executables, DLLs, and drivers with a certificate so Windows can verify the file's publisher and that it has not been tampered with. Signatures chain to a trusted Certificate Authority.

  • DSE (Driver Signature Enforcement) : 64-bit Windows refuses to load unsigned kernel drivers; this is a key kernel-integrity control.
  • Catalog vs Embedded : signatures can be embedded in the file or held in a system catalog (.cat).
  • Why it matters : auditors flag unsigned or invalidly signed binaries in sensitive locations; attackers seek stolen certs or signed-but-vulnerable drivers (BYOVD).
# PowerShell: verify a file's signature
Get-AuthenticodeSignature C:\Windows\System32\cmd.exe |
    Select Status, SignerCertificate

signtool verify /pa app.exe             :: verify (Windows SDK)
Get-Process lsass | Select Path, Company  # basic process info

Authentication & Logon

All Windows security decisions are based on SIDs (Security Identifiers) and access tokens, coordinated by the LSA (Local Security Authority) inside lsass.exe.

Core Concepts -
  • SID (Security Identifier) : A unique value identifying a user, group, or computer, e.g. S-1-5-21-...-1001. Names are just labels; permissions are stored against SIDs. Well-known SIDs include S-1-5-18 (SYSTEM) and S-1-5-32-544 (Administrators).
  • Access Token : Attached to every process; lists the user's SID, group SIDs, and privileges. Created at logon and checked on every access.
  • Security Descriptor : Attached to every securable object (file, key, service); contains the owner SID and the DACL.
  • LSASS : Validates credentials, issues tokens, and caches secrets in memory, which is why it is a prime target for credential theft.
Logon Flow -
User enters credentials (winlogon / LogonUI)
   -> LSASS selects an authentication package
      -> Local account?  -> verify against SAM
      -> Domain account? -> Kerberos / NTLM to a Domain Controller
   -> on success: LSASS builds an access token (SIDs + privileges)
      -> winlogon starts the user's shell (explorer.exe) with that token
Logon Types -
  • Interactive : at the physical keyboard.
  • Network : accessing a share or service remotely (no interactive desktop).
  • RemoteInteractive : Remote Desktop (RDP).
  • Service / Batch : for services and scheduled tasks.
Authentication Factors -
  • Password : verified against the SAM (local) or a Domain Controller.
  • Windows Hello : biometric (face, fingerprint) or PIN, backed by the TPM. The PIN is device-local, not a password sent over the network.
  • Smart Card / FIDO2 : hardware-backed certificate or security-key logon.

SAM & Hashes

The SAM (Security Account Manager) is the database of local user accounts and their password hashes on a standalone (non-domain) machine. On a domain controller, this role is handled instead by the Active Directory database (NTDS.dit).

Where It Lives -
  • File : C:\Windows\System32\config\SAM, loaded as the HKLM\SAM hive. It is locked while Windows runs and is not readable even by administrators through normal file access.
  • Encryption : Hashes in the SAM are further encrypted with a key called SYSKEY, stored in the SYSTEM hive.
Password Hashes -
  • LM Hash : The legacy LAN Manager hash. Weak (case-insensitive, split into two 7-character halves) and disabled by default since Windows Vista. Should never be enabled.
  • NT Hash : The current format: an unsalted MD4 hash of the password (UTF-16). Because it is unsalted, identical passwords produce identical hashes.
Pass-the-Hash : Because NTLM authentication proves knowledge of the NT hash rather than the plaintext password, a stolen hash alone can be replayed to authenticate, without ever cracking it. This is a core reason the SAM and LSASS memory are sensitive, and why defenses like Credential Guard exist.

For any hands-on work with SAM/hash extraction, do it only on systems you own or are explicitly authorized to test.

NTLM & Kerberos

Windows has two main network authentication protocols. Kerberos is the modern default inside a domain; NTLM is the older challenge-response protocol, kept for backward compatibility and non-domain scenarios.

• NTLM :

NTLM proves the client knows the NT hash without sending it, using a challenge-response handshake.

1. Client -> Server : "I want to log in as Rahul"  (NEGOTIATE)
2. Server -> Client : random challenge (nonce)     (CHALLENGE)
3. Client -> Server : challenge encrypted with the NT hash (AUTHENTICATE)
4. Server validates the response (via the DC for domain accounts)
  • Stateless & no DC trust of server : Works without a trusted third party, which is also its weakness.
  • Weaknesses : No mutual authentication (server is not verified), vulnerable to pass-the-hash and relay attacks. Microsoft is actively deprecating it.
• Kerberos :

Kerberos uses a trusted third party, the KDC (Key Distribution Center, running on every Domain Controller), and time-limited tickets so passwords are never sent over the network after the initial logon.

1. Client -> KDC (AS)  : request, proof derived from password
   KDC -> Client        : TGT (Ticket Granting Ticket), encrypted with krbtgt key
2. Client -> KDC (TGS) : "I have a TGT, give me a ticket for FileServer"
   KDC -> Client        : Service Ticket for FileServer
3. Client -> FileServer: Service Ticket  -> access granted (mutual auth)
  • TGT : Proves who you are; obtained once at logon, reused for service requests.
  • Service Ticket : Grants access to one specific service (identified by its SPN, Service Principal Name).
  • Advantages : Mutual authentication, no repeated password use, tickets expire. Requires synchronized clocks (within ~5 minutes) and a reachable DC.
NTLM Kerberos
Model challenge-response ticket-based
Third party none KDC (Domain Controller)
Mutual auth no yes
Default in a domain fallback only yes

Credential Storage

Windows provides several protected stores so applications never have to keep passwords in plain text.

• Credential Manager :

A per-user vault for saved logins, split into Web Credentials (browsers, apps) and Windows Credentials (network shares, RDP, domain logins). The data is encrypted with DPAPI and stored in the user's profile.

control /name Microsoft.CredentialManager   :: open the GUI
cmdkey /list                                 :: list stored credentials
cmdkey /add:server01 /user:Rahul /pass       :: store a credential
cmdkey /delete:server01                      :: remove one

# PowerShell (via the CredentialManager module)
Get-StoredCredential -Target "server01"
• DPAPI (Data Protection API) :

The underlying encryption service used by Credential Manager, browsers, and many apps. CryptProtectData / CryptUnprotectData encrypt data with a key derived from the user's logon password, so only that user (on that machine) can decrypt it. No app has to manage its own key.

• Windows Hello & Passkeys :

Hello stores credentials in a hardware-backed container tied to the TPM and unlocked by biometrics or a PIN. The private key never leaves the device, making it phishing-resistant.

• Credential Guard :

On supported editions, Credential Guard uses virtualization-based security (VBS) to run LSASS secrets inside an isolated hypervisor container (the "Isolated LSA"). Even an administrator or malware with kernel access on the main OS cannot read the cached hashes and Kerberos tickets, which blocks pass-the-hash and credential dumping.

• LSA Protection :

Runs lsass.exe as a Protected Process Light (PPL) so other processes cannot read its memory or inject into it.

Stores at a Glance -
Store Protects Backed By
Credential Manager saved app / network logins DPAPI
DPAPI any app secret user logon key
Windows Hello logon keys / passkeys TPM + biometrics
Credential Guard LSASS secrets VBS / hypervisor

UAC & Privileges

• UAC (User Account Control) :

UAC limits the damage an account can do by running even administrators with a standard-user token most of the time. When an action needs admin rights, Windows shows a consent prompt to elevate.

  • Split Token : At logon, an admin receives two tokens: a filtered standard token (used by default) and a full admin token (used only after elevation).
  • Elevation : "Run as administrator" or a UAC prompt switches to the full token for that one process.
  • Integrity Levels : Every process has a Mandatory Integrity Level: Low, Medium (normal user), High (elevated admin), or System. A lower-integrity process cannot write to a higher-integrity object.
  • Secure Desktop : The dimmed UAC prompt runs on an isolated desktop so other programs cannot click it automatically.
# PowerShell: am I running elevated?
([Security.Principal.WindowsPrincipal] `
  [Security.Principal.WindowsIdentity]::GetCurrent()
).IsInRole([Security.Principal.WindowsBuiltinRole]::Administrator)

Start-Process powershell -Verb RunAs    # relaunch elevated
runas /user:Administrator cmd           :: run as another user
• Privileges & Rights :

Beyond file permissions, an account holds privileges: system-wide capabilities listed in its token, assigned via Local Security Policy (secpol.msc) or Group Policy.

  • SeDebugPrivilege : debug and read the memory of other processes.
  • SeBackupPrivilege / SeRestorePrivilege : read/write any file, bypassing ACLs, for backups.
  • SeShutdownPrivilege : shut down the system.
  • SeTakeOwnershipPrivilege : take ownership of any object.
whoami /priv        :: list current privileges
whoami /groups      :: list group SIDs and integrity level
whoami /all         :: everything about the current token
Built-in Accounts -
  • SYSTEM : the local OS account, more powerful than Administrator; used by services.
  • Administrator : the built-in local admin (disabled by default on modern Windows).
  • Local Service / Network Service : low-privilege accounts for services.
  • TrustedInstaller : owns Windows system files; even admins must take ownership to modify them.

Security & Defenses

The sections above describe the attack surface; this one covers the built-in controls an auditor checks for hardening. Windows layers several defenses (defense in depth).

• Microsoft Defender Antivirus :

The built-in anti-malware engine, with real-time protection, cloud-delivered detection, and controlled folder access (anti-ransomware).

Get-MpComputerStatus          # engine state, real-time protection on/off
Get-MpThreat                  # detected threats
Get-MpPreference              # configuration (exclusions etc.)
Start-MpScan -ScanType QuickScan
"C:\Program Files\...\MpCmdRun.exe" -Scan -ScanType 1

Auditors review exclusions (over-broad exclusions weaken protection) and whether real-time protection or tamper protection is off.

• Attack Surface Reduction (ASR) :

A set of Defender rules that block common attack techniques: Office apps spawning child processes, credential theft from LSASS, executables from email, obfuscated scripts, and more. Rules run in Audit or Block mode.

• Application Control :
  • AppLocker : allow/deny which executables, scripts, installers, and DLLs can run, by path, publisher, or hash. Configured via Group Policy.
  • WDAC (App Control for Business) : a stronger, kernel-enforced code-integrity policy that whitelists trusted code system-wide; harder to bypass than AppLocker.
  • SmartScreen : reputation-based blocking of unknown apps and sites; triggered on downloaded files via the Mark of the Web (see NTFS).
• Windows Firewall :

Host firewall with three profiles (Domain, Private, Public), each with inbound/outbound rules. Default-deny inbound is the baseline.

netsh advfirewall show allprofiles      :: profile state
netsh advfirewall firewall add rule name="Block8080" ^
    dir=in action=block protocol=TCP localport=8080

# PowerShell

• Virtualization-Based Security (VBS) :

Uses the hypervisor to isolate sensitive data from the OS. It underpins Credential Guard (protects LSASS secrets, see Credential Storage) and HVCI / Memory Integrity (verifies kernel drivers in an isolated environment).

• PowerShell Security :

PowerShell is both an admin tool and a common attack tool, so it has its own controls (full detail in the PowerShell cheatsheet):

  • Execution Policy : controls whether scripts run and must be signed (a safety setting, not a security boundary).
  • AMSI (Antimalware Scan Interface) : lets Defender scan scripts and in-memory code at runtime, even when obfuscated; attackers frequently try to bypass it.
  • Script Block & Module Logging : records executed code to the event log (event ID 4104) for auditing.
  • Constrained Language Mode : restricts dangerous language features when application control is enforced.

Auditing & Logging

Windows records activity in structured event logs (viewable in eventvwr.msc, queryable with wevtutil or Get-WinEvent). What gets logged is governed by the audit policy. This is the auditor's primary evidence source.

Main Logs -
  • Security : logons, privilege use, object access, account and policy changes.
  • System : drivers, services, hardware.
  • Application : app and service messages.
  • Operational logs : per-component channels under Applications and Services Logs (PowerShell, Sysmon, Task Scheduler, etc.).
Audit Policy -
auditpol /get /category:*                 :: current audit settings
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
secpol.msc                                :: Local Security Policy (GUI)

Advanced audit policy (and Group Policy in a domain) controls subcategories like Logon, Process Creation, and Object Access. Process-creation auditing (and logging the command line) is a high-value setting often missing.

Sysmon -

A free Sysinternals driver that adds detailed, tamper-resistant security logging far beyond the defaults, driven by a config file. It is the de-facto standard for endpoint visibility.

  • Event 1 : process creation (with hashes and command line).
  • Event 3 : network connection.
  • Event 7 : image (DLL) loaded, useful for spotting DLL hijacks.
  • Event 11 : file created. Event 13 : registry value set.

Logs land in Microsoft-Windows-Sysmon/Operational and are usually forwarded to a SIEM.

ETW (Event Tracing for Windows) -

The high-performance tracing framework underneath the event logs. Providers emit events, sessions collect them, and consumers read them. Most logging (including Sysmon and many EDRs) is built on ETW; manage sessions with logman or wpr.

Active Directory

Active Directory (AD) is Microsoft's directory service for managing users, computers, and resources centrally across a network. Instead of every machine keeping its own local accounts (SAM), a domain stores identities centrally and every member machine trusts it.

Structure -
  • Domain : A security and administrative boundary sharing one AD database, e.g. corp.example.com.
  • Domain Controller (DC) : A server running AD Domain Services (AD DS) that authenticates users and holds a copy of the directory (the NTDS.dit database). DCs also run the Kerberos KDC and DNS.
  • Tree : One or more domains sharing a contiguous namespace.
  • Forest : The top-level container: one or more trees that trust each other. The forest is the real security boundary.
  • OU (Organizational Unit) : A folder inside a domain for grouping objects and applying policy.
  • Objects : Users, groups, computers, printers, each with attributes, identified by a Distinguished Name (CN=Rahul,OU=IT,DC=corp,DC=example,DC=com).
Key Services -
  • Authentication : Domain logons use Kerberos (see above) against a DC.
  • Group Policy (GPO) : Centrally enforces settings, security policy, and software on users and computers. Managed with gpmc.msc; refresh with gpupdate /force.
  • LDAP : The protocol used to query and modify the directory (port 389, or 636 for LDAPS).
  • Global Catalog : A forest-wide searchable index of objects.
  • Trusts : Relationships that let users in one domain access resources in another.
  • Azure AD / Entra ID : The cloud identity service for Microsoft 365 and cloud apps; related to but distinct from on-premises AD.
whoami /fqdn                              :: your distinguished name
nltest /dsgetdc:corp.example.com          :: find a domain controller
gpresult /r                               :: policies applied to you
gpupdate /force                           :: reapply Group Policy now

WMI & CIM

WMI (Windows Management Instrumentation) is the built-in framework for querying and managing almost everything about a Windows system, locally or remotely: hardware, OS, processes, services, event logs, and more. It is Microsoft's implementation of the industry-standard CIM (Common Information Model).

Concepts -
  • Classes : Managed things are modeled as classes like Win32_Process, Win32_Service, Win32_OperatingSystem, Win32_LogicalDisk.
  • Namespace : Classes are organized under namespaces, mainly root\CIMV2.
  • WQL : An SQL-like query language for WMI, e.g. SELECT * FROM Win32_Process WHERE Name='notepad.exe'.
  • Providers : Components that supply data for classes.
  • WMI as attack surface : Its power and remote reach make it popular for both administration and for persistence/lateral movement by attackers, so it is heavily logged.
Accessing WMI -

Use the modern CIM cmdlets (Get-CimInstance) in PowerShell; the older Get-WmiObject and the wmic command are deprecated.

# Preferred: CIM cmdlets
Get-CimInstance Win32_OperatingSystem | Select Caption, Version, BuildNumber
Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
    Select DeviceID, @{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB)}}
Get-CimInstance Win32_Service -Filter "State='Running'" | Select Name
Get-CimInstance -Query "SELECT * FROM Win32_Process WHERE Name='explorer.exe'"

# Remote query
Get-CimInstance Win32_BIOS -ComputerName Server01

# Legacy (deprecated), still seen in older scripts:
wmic process list brief

System State & Recovery

Windows keeps multiple snapshots and logs of its configuration so it can be recovered after a bad update, driver, or crash.

System State -

"System State" is a backup concept covering the critical configuration that makes a Windows install bootable and consistent: the registry, boot files, the COM+ database, and, on a DC, Active Directory. It is backed up as a unit with wbadmin.

  • System Restore : Creates restore points (registry + system files) before major changes, using Volume Shadow Copy. Roll back without touching personal files.
  • Volume Shadow Copy (VSS) : Point-in-time snapshots of a volume; also powers "Previous Versions" of files and most backup software.
  • Reset / Recovery : "Reset this PC" reinstalls Windows keeping or removing files; WinRE provides repair tools offline.
  • Hibernation : Saves RAM to hiberfil.sys and powers off; Fast Startup is a hybrid that hibernates only the kernel session.
Recovery Tools -
sfc /scannow                    :: scan and repair system files
DISM /Online /Cleanup-Image /RestoreHealth   :: repair the component store
rstrui                          :: open System Restore
wbadmin start systemstatebackup -backupTarget:E:   :: back up system state
vssadmin list shadows           :: list shadow copies

For event logs and what the system records, see Auditing & Logging.
